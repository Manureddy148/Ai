1 Executive Summary

This document describes the architecture of a record-linkage system for the Amazon ML Challenge on Business Entity Resolution. The system links every Source 1 business record to the Source 2 and Source 3 records that describe the same business, or declares it a singleton, using only the provided files. It is one Python module, er_pipeline.py, with the stages load, normalise, block, pair features, LightGBM matcher, (threshold, ratio) decode and TSV output. Every design decision follows from the metric: macro-averaged F0.5 per Source 1 entity, where a singleton scores 1.0 only when the predicted list is empty.

1.1 Purpose and scope

The document serves two audiences. For challenge reviewers it is the technical companion to the methodology write-up: it explains, at the level of functions, regular expressions and parameter values, how the pipeline turns the input files into matching_results.tsv and candidate_pairs.tsv, and why each stage is shaped as it is. For maintainers it is the reference for the data contracts between stages, the memory budget, the validation protocol and the known limitations. Every claim is tied to the code in er_pipeline.py. The pipeline has not yet been executed on the challenge data; any quantity that only a run can produce is marked to be filled from the run log, and no measured result appears in this document.

1.2 The problem

Three independent sources describe the same population of businesses without a shared identifier. Each record carries an entity_id whose prefix (S1-, S2-, S3-) names its source, a free-text business_name, a free-text business_address and a country label. Source 1 is the deduplicated reference: a Source 1 entity may correspond to zero, one or many records in Sources 2 and 3, while a Source 2 or 3 record belongs to at most one Source 1 entity. The fields carry the noise typical of business directories: abbreviated or expanded legal forms, trade names introduced by markers such as dba, ampersands versus and, transposed or missing tokens, typos, abbreviated street types, missing postal codes and landmark-based addresses. Training data cover the United States and India with a ground-truth file; the test data add France, never seen in training, whose records must all be resolved (see Chapter 3).

The scoring rule shapes the solution more than any property of the data. For each Source 1 entity the organisers compute F0.5 = 1.25·P·R / (0.25·P + R), with P and R the precision and recall of the predicted list against the true list, and average over all Source 1 entities. With β = 0.5 precision is weighted twice as heavily as recall: one wrongly merged record costs more than one missed record. Singletons are included and scored in a binary way: an entity with no true match earns 1.0 if the predicted list is empty and 0.0 otherwise. A system must therefore be conservative on every entity and treat "no match" as a first-class prediction (see Chapter 2).

1.3 The solution

The system is a supervised record-linkage pipeline with the seven stages of Figure 1.1. Load (load_split()) reads the three source files of a split with an explicit tab separator, no quoting and no missing-value parsing, concatenates Sources 2 and 3 into one frame, and parses the ground truth into a dictionary from Source 1 id to a set of matched ids. Normalise (prep()) derives for every record an ASCII-folded, abbreviation-expanded name (name_n), a core name with legal forms removed (name_c), alias variants split on markers such as dba (name_alts), a normalised, stop-word-free address (addr_n, addr_c), the postal code, the digit runs, the leading house number and a normalised country. Block (block()) fits TF-IDF character 2–4-gram vectorisers on three views (core name, name plus address, address) and, within each country, retrieves the top-k Source 2/3 neighbours per view (k = 25, 25 and 10) with the chunked sparse product in topk_sparse(); a fourth view restricted to a shared postal code adds up to 10 name-cosine neighbours. The union, filtered at cosine > 0.05, is the candidate table and is written verbatim as candidate_pairs.tsv.

Features (features()) computes per candidate pair the three view cosines, rapidfuzz and Jaro-Winkler similarities on core names, token Jaccard, first-token, initials, alias and acronym agreement, address similarities, ternary postal-code and house-number agreement, street-number overlap and conflict, lengths, a source flag, and contextual features that compare the pair with the competing candidates of the same Source 1 entity and of the same Source 2/3 record (gap to the best competitor, rank, candidate count). Match trains a LightGBM binary classifier on the labelled training pairs with 5-fold GroupKFold grouped by Source 1 entity, yielding out-of-fold probabilities and a final model refit on all pairs. Decode (decode_table(), decide()) assigns each Source 2/3 record to the Source 1 entity that scores it highest and keeps a pair only when its probability reaches an absolute threshold and a fixed fraction of the best probability in its (Source 1, source) group; (thr, ratio) is chosen by exhaustive sweep on the out-of-fold macro F0.5 from macro_f05() over all training entities, singletons included. Write emits one row per test Source 1 entity in each TSV with de-duplicated id lists.

1.4 Key design principles

Five principles run through every stage; Table 1.1 records where each is realised in the code.

  • Precision first. Because F0.5 penalises a false merge more than a missed link, the decision layer never uses a naive 0.5 cut-off: it combines an absolute threshold, a relative ratio to the strongest competitor in the same (Source 1, source) group and a one-Source-1-per-record constraint, and selects the operating point directly on the official metric.
  • Singleton awareness. f05() reproduces the organisers' rule exactly, and the (thr, ratio) sweep averages over every training entity, so the cost of a spurious link on a singleton is part of the objective being optimised.
  • Open-set country. Country only partitions blocking; a label absent from Sources 2 and 3 falls back to the whole index, the normalisation tables include French legal forms and address idioms, and the vectorisers are refit per split, so France is handled without any code path that names it.
  • Memory-bounded computation. Top-k retrieval densifies one chunk of Source 1 rows at a time, sized from the block width to a budget of 2×107 cells, and pair cosines are computed in slices of 200,000 pairs, so peak memory does not grow with a country block or the candidate table.
  • No external data. The only inputs are the provided TSVs; there is no gazetteer, registry, geocoder, pretrained model or web access, and the matcher is an MIT-licensed LightGBM ensemble far below the 8-billion-parameter limit.

1.5 What is delivered

The package follows the structure the organisers require. code/business_entity_resolution/src/er_pipeline.py is the complete pipeline; requirements.txt pins its dependencies (NumPy, pandas, scikit-learn, rapidfuzz, LightGBM) and README.md gives the run command. utils/validate_submission.py checks both output files against every formatting rule, and utils/score.py computes macro F0.5 on a labelled split. notebooks/kaggle_run.ipynb runs the script in a Kaggle session, where the data directory is auto-detected under /kaggle/input, and packages the zip. Documentation_template.md holds the methodology write-up, and this document sits under docs/architecture/. The output/ folder receives matching_results.tsv and candidate_pairs.tsv once the pipeline has been run (see Chapter 11).

Risk. Every quantitative claim is conditional on a run that has not yet taken place. Blocking recall, out-of-fold macro F0.5, the selected (thr, ratio) and per-country match rates remain placeholders until the run log exists (Chapters 10 and 12).
