11 Outputs, Packaging and Reproducibility

The pipeline ends where the organisers' tooling begins: two tab-separated files, a zip archive with a fixed layout, and the claim that anyone can regenerate the files from the training and test data alone. This chapter documents the writer loop in main(), the invariants that make both files pass validation by construction, the repository and package layout, the Kaggle notebook cell by cell with its dataset mirrors, and the sources of non-determinism a bit-exact re-run must control. Numbers that come from an actual run are marked as placeholders; nothing measured is reported.

11.1 The output files

11.1.1 The writer code path

Both files are written by one loop at the end of main(), after decide() has selected the test pairs (see Chapter 9). Its inputs are two dictionaries built by to_lists(): matches, from the decoded pairs, and cands, from fte[["i1", "i2"]], the full test feature table. to_lists() starts from {e: [] for e in s1.entity_id}, so every test S1 entity owns a key before any pair is appended; an entity with no surviving pair, or no candidate at all, keeps an empty list instead of vanishing from the output.

for fname, col, lists in [("matching_results.tsv", "matched_entity_ids", matches),
                          ("candidate_pairs.tsv", "candidate_entity_ids", cands)]:
    path = os.path.join(args.out_dir, fname)
    with open(path, "w", newline="") as fh:
        fh.write(f"source1_entity_id\t{col}\n")
        for e in te1.entity_id.values:
            fh.write(f"{e}\t{','.join(dict.fromkeys(lists[e]))}\n")
    log(f"wrote {path}")

Four details carry the format guarantees. The header is a literal f-string with one tab, so the column names are exactly those of the specification; nothing is delegated to DataFrame.to_csv(), whose index, quoting and line-terminator defaults would each need overriding. Rows follow te1.entity_id.values, the S1 test frame after prep(), which calls reset_index(drop=True) but never reorders, so output order and row count equal those of test_source1.tsv. Each list passes through dict.fromkeys(), which keeps insertion order and collapses repeated keys, before the comma join. The file is opened with newline="", which disables platform newline translation, so the explicit \n is written verbatim and a Windows run cannot glue a carriage return to the last id of a row.

Duplicates inside a list are already impossible upstream: block() ends with drop_duplicates() on (i1, i2) and decode_table() keeps each S2/S3 row for one S1 only, so dict.fromkeys() is a guard, not a repair. An empty list joins to the empty string, so a singleton row is the id, a tab and a newline, exactly the third example row of the problem statement.

11.2 candidate_pairs.tsv: the set the model scores

The problem statement defines candidate_pairs.tsv as the exact set of records fed to the matching model for inference, not the output of an early blocking pass that is later filtered. The pipeline meets this definition literally. cte = block(te1, te2) is the only candidate-generation stage; fte = features(cte, te1, te2) starts from cand.copy() and only assigns columns, so it neither adds nor removes rows; pte = model.predict(fte[feats]) scores every row; and cands = to_lists(fte[["i1", "i2"]], te1, te2) converts the same rows to id lists. The organisers' recall-ceiling and reduction-ratio analysis of this file therefore describes precisely what the LightGBM model saw.

The subset property follows from the same flow. decode_table(fte, pte) takes fte[["i1", "i2", "is_s3"]], attaches probabilities and drops rows via drop_duplicates("i2"), but never creates any; decide() is a boolean mask over that table. Every row of matches is thus a row of fte, and the validator's cross-check can fail only when the two files come from different invocations.

Design note. The candidate file is much larger than the match file: each S1 entity carries up to 25 + 25 + 10 + 10 = 70 candidates before the per-view sc > 0.05 cosine cut and the de-duplication of the union (see Chapter 6), against the few that survive decide(). Because F0.5 is precision-weighted and a singleton scores 1.0 only when predicted empty, the gap between the files is the visible record of how much the matcher and decision layer remove.

11.3 Repository layout and the submission package

The repository keeps the pipeline in the layout the challenge prescribes for the zip, so packaging is a copy rather than a restructuring. code/business_entity_resolution/ holds src/er_pipeline.py, the pipeline README.md and requirements.txt; Documentation_template.md at the root is the methodology write-up; utils/ contains the stdlib-only validator and scorer plus a synthetic-data generator; notebooks/kaggle_run.ipynb is the runner of Section 11.4; docs/ carries this document; output/ receives the generated TSVs. The dataset, zip archives and output/*.tsv are excluded by .gitignore.

The archive is <team_name>_submission.zip with the structure of Figure 11.1: the two output files, the self-contained code folder and the methodology document, nothing else. The organisers use it to reproduce results, audit blocking and check fair play and licensing (see Chapter 13), so the code folder must run alone: er_pipeline.py imports, beyond the standard library, only NumPy, pandas, scikit-learn, LightGBM and rapidfuzz (SciPy is used indirectly through the sparse TF-IDF matrices), and installs rapidfuzz through pip when its import fails.

11.4.2 Code acquisition

Cell 3 assumes that the branch named in RAW_BASE has been pushed; a raw URL for a local-only branch returns HTTP 404. When the repository is not pushed, or the kernel has no internet, the fallback is to upload the three files into /kaggle/working by hand (Kaggle sidebar, Add data, Upload) and re-run the cell; the same applies to the files fetched in cell 6, whose warning names the missing file to add to the package folder before zipping. Attaching a repository snapshot as a Kaggle dataset and replacing fetch() with a shutil.copy() from /kaggle/input for each entry of FILES removes the dependency on the branch name.

Risk. The zip must be built from the output directory the validator checked, in the same session. Re-running cell 4 regenerates both TSVs, and because LightGBM is not seeded (Section 11.5) the new matching_results.tsv can differ in a few borderline pairs from the one uploaded to the leaderboard. Run cells 4, 5 and 6 once, in order, and upload the leaderboard file from the same /kaggle/working/output.

11.5 Determinism

Most of the pipeline is a pure function of the data and library versions: TfidfVectorizer vocabularies, the sparse products in topk_sparse(), np.argpartition, rapidfuzz scores, GroupKFold (which never shuffles) and the (thr, ratio) grid. The stochastic component is LightGBM. The params dictionary in main() sets feature_fraction=0.8, bagging_fraction=0.8 and bagging_freq=1, so every tree is grown on a random 80 % of rows and columns, but sets no seed. LightGBM then uses its built-in default seeds, which keeps a single-threaded run repeatable, while n_jobs=-1 lets histogram construction be split across threads in an order that varies between machines and builds. The OOF probabilities, the fold best iterations, the refit round count int(np.mean(iters) * 1.1) and a few borderline decisions can therefore differ between environments.

The recommended follow-up is to add seed=42, deterministic=True and force_row_wise=True to params, so that LightGBM neither draws unseeded samples nor picks its histogram strategy by timing; this costs some speed and changes nothing in the OOF sweep or the decision layer. A minor second source is tie-breaking: decode_table() sorts by probability with the default quicksort, which is not stable, so bit-identical probabilities could be ordered differently across NumPy versions; kind="stable" removes this. Documentation_template.md already calls for a seed for bit-exact reproduction.

11.6 Dependency pinning

requirements.txt currently states lower bounds (numpy>=1.24, pandas>=2.0, scipy>=1.10, scikit-learn>=1.3, lightgbm>=4.0, rapidfuzz>=3.0). Lower bounds document the API assumptions, such as the callback form lgb.early_stopping(100, verbose=False) that LightGBM 4 makes the only early-stopping interface, but neither satisfy the package specification's request for pinned versions nor fix the floating-point behaviour on which Section 11.5 depends. Before the final zip, the versions of the environment that produced the submitted files should be captured with pip freeze restricted to these six packages, written as exact == pins with the Python version in a comment, and re-installed in a clean environment to confirm that the validator passes and the output files are identical.

11.8 Run-time expectations

The stages scale differently. Blocking is bounded by the chunked sparse products of topk_sparse(), about 2·107 dense cells per chunk (see Chapter 12). Pair features in features() are Python-level list comprehensions over the candidate table, at least one rapidfuzz call per string feature per pair (n_alias_best makes one per alias combination), and are expected to dominate wall-clock time; their cost is linear in the pair count the log reports as pairs per S1. LightGBM runs five folds with early stopping plus one refit on all cores. For the synthetic smoke test of 3,000 training and 1,500 test S1 entities generated by make_synthetic_dataset.py, the repository README reports about 30 s end to end; this figure is quoted from the README, not measured for this document, and says nothing about the real data.
