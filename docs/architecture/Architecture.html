1 Executive Summary

This document describes the architecture of a record-linkage system for the Amazon ML Challenge on Business Entity Resolution. The system links every Source 1 business record to the Source 2 and Source 3 records that describe the same business, or declares it a singleton, using only the provided files. It is one Python module, er_pipeline.py, with the stages load, normalise, block, pair features, LightGBM matcher, (threshold, ratio) decode and TSV output. Every design decision follows from the metric: macro-averaged F0.5 per Source 1 entity, where a singleton scores 1.0 only when the predicted list is empty.

1.1 Purpose and scope

The document serves two audiences. For challenge reviewers it is the technical companion to the methodology write-up: it explains, at the level of functions, regular expressions and parameter values, how the pipeline turns the input files into matching_results.tsv and candidate_pairs.tsv, and why each stage is shaped as it is. For maintainers it is the reference for the data contracts between stages, the memory budget, the validation protocol and the known limitations. Every claim is tied to the code in er_pipeline.py. The pipeline has not yet been executed on the challenge data; any quantity that only a run can produce is marked to be filled from the run log.

1.2 The problem

Three independent sources describe the same population of businesses without a shared identifier. Each record carries an entity_id whose prefix (S1-, S2-, S3-) names its source, a free-text business_name, a free-text business_address and a country label. Source 1 is the deduplicated reference: a Source 1 entity may correspond to zero, one or many records in Sources 2 and 3, and because no two Source 1 records denote the same business, the pipeline assumes that a Source 2 or 3 record belongs to at most one Source 1 entity (Chapter 2). The fields carry the noise typical of business directories: abbreviated or expanded legal forms, trade names introduced by markers such as dba, ampersands versus and, transposed tokens, typos, abbreviated street types, missing postal codes and landmark-based addresses. Training data cover the United States and India with a ground-truth file; the test data add France, never seen in training, whose records must all be resolved (see Chapter 3).

The scoring rule shapes the solution more than any property of the data. For each Source 1 entity the organisers compute F0.5 = 1.25·P·R / (0.25·P + R), with P and R the precision and recall of the predicted list against the true list, and average over all Source 1 entities. With β = 0.5 precision is weighted twice as heavily as recall: one wrongly merged record costs more than one missed record. Singletons are included and scored in a binary way: an entity with no true match earns 1.0 if the predicted list is empty and 0.0 otherwise. A system must therefore be conservative on every entity and treat "no match" as a first-class prediction (see Chapter 2).

1.3 The solution

The system is a supervised record-linkage pipeline with the seven stages of Figure 1.1. Load (load_split()) reads the three tab-separated source files of a split as strings, concatenates Sources 2 and 3 into one frame, and parses the ground truth into a dictionary from Source 1 id to a set of matched ids. Normalise (prep()) derives for every record an ASCII-folded, abbreviation-expanded name (name_n), a core name without legal forms (name_c), alias variants split on markers such as dba (name_alts), a stop-word-free address (addr_c), the postal code, the digit runs and the leading house number. Block (block()) fits TF-IDF character 2–4-gram vectorisers on the split's own texts for three views (core name, name plus address, address) and, within each country, retrieves the top-k Source 2/3 neighbours per view (k = 25, 25 and 10) with the chunked sparse product in topk_sparse(); a fourth view restricted to a shared postal code adds up to 10 name-cosine neighbours. Each view keeps only pairs with cosine above 0.05; the de-duplicated union of the four views is the candidate table, which is exactly the set the matcher scores and which is written, as one id list per Source 1 entity, to candidate_pairs.tsv.

Features (features()) computes per candidate pair the view cosines, rapidfuzz and Jaro-Winkler similarities, token Jaccard, first-token, initials, alias and acronym agreement, address similarities, ternary postal-code and house-number agreement, street-number overlap and conflict, lengths, a source flag, and contextual features that compare the pair with the other candidates of the same Source 1 entity and of the same Source 2/3 record (gap to the best value in the group, so that the best candidate has gap 0; rank by cos_full; candidate count). Match trains a LightGBM binary classifier on the labelled training pairs with 5-fold GroupKFold grouped by Source 1 entity and early stopping on the held-out fold, yielding out-of-fold probabilities, and then refits a final model on all pairs for 1.1 times the mean best iteration of the folds. Decode (decode_table(), decide()) assigns each Source 2/3 record to the Source 1 entity that scores it highest and keeps a pair only when its probability reaches an absolute threshold and a fixed fraction of the best probability in its (Source 1, source) group; (thr, ratio) is chosen by exhaustive sweep on the out-of-fold macro F0.5 from macro_f05(), singletons included. Write emits one row per test Source 1 entity in each TSV with de-duplicated id lists.

1.4 Key design principles

Six principles run through every stage; Table 1.1 records where each is realised in the code.

  • Precision first. Because F0.5 penalises a false merge more than a missed link, the decision layer never uses a naive 0.5 cut-off: it combines an absolute threshold, a relative ratio to the strongest competitor in the same (Source 1, source) group and a one-Source-1-per-record constraint, and selects the operating point directly on the official metric.
  • Singleton awareness. f05() reproduces the organisers' rule exactly, and the (thr, ratio) sweep averages over every training entity, so the cost of a spurious link on a singleton is part of the objective being optimised.
  • Open-set country. Country only partitions blocking; a label absent from Sources 2 and 3 falls back to the whole index, the normalisation tables include French legal forms and address idioms, and the vectorisers are refit per split, so France is handled without any code path that names it.
  • Memory-bounded computation. Top-k retrieval densifies one chunk of Source 1 rows at a time, sized from the block width to a budget of 2×107 cells, and pair cosines are computed in slices of 200,000 pairs, so peak memory does not grow with a country block or the candidate table.
  • No external data. The only inputs are the provided TSVs; there is no gazetteer, registry, geocoder, pretrained model or web access, and the matcher is an MIT-licensed LightGBM ensemble far below the 8-billion-parameter limit.
  • Train/test parity. The training and the test split pass through the same prep(), block() and features() calls with the same parameters, so the feature distribution the matcher was fitted on is the one it scores at inference, and the operating point chosen on out-of-fold probabilities transfers without adjustment. The same candidate table feeds both the matcher and candidate_pairs.tsv, so the rule that every matched id must also be a candidate holds by construction rather than by a post-hoc check.

2 Problem Statement and Evaluation Metric

This chapter states the task as the challenge defines it, fixes the file formats the pipeline must read and write, and derives the evaluation metric from first principles. The metric is a macro-average of the per-entity F0.5 score over every Source 1 entity, with an all-or-nothing rule for entities that have no true match. Precision weighting, equal weight per entity and the singleton rule each shape one or more stages of the pipeline described in Chapters 5 to 11; the closing table maps those consequences to the functions in er_pipeline.py that implement them.

2.1 Formal task definition

Three independent data sources describe overlapping sets of real-world businesses. Each record carries a free-text business name, a free-text address and a country label, but no shared key. Source 1 (S1) is designated the deduplicated reference source: every S1 record stands for a distinct real-world entity. Source 2 (S2) and Source 3 (S3) are the sources to be linked. The task is, for every S1 record, to return the set of S2 and S3 records that describe the same business. That set may be empty (the S1 entity is a singleton), contain one record, or contain many records, possibly from both S2 and S3. Neither S2-to-S3 nor S1-to-S1 links are requested; a self-match to an S1 identifier is a validation error.

Formally, let E be the set of S1 entities and O the union of S2 and S3 records. The ground truth is a function g: E → 2O assigning each S1 entity a (possibly empty) subset of O; a submission is another function h: E → 2O on the same domain, with every element of E appearing exactly once. load_split() reads g from train_ground_truth.tsv into a dictionary from S1 identifier to a Python set, discarding empty tokens so that a blank list becomes the empty set.

One structural assumption follows from S1 being deduplicated: because two S1 records never denote the same business, an S2 or S3 record belongs to the ground-truth set of at most one S1 entity. The decision layer exploits this in decode_table(), which keeps each S2/S3 record only in the pair where it scores highest (see Chapter 9).

The country label is an open set. Training records are labelled US or India; test records additionally carry France, which never occurs in training. The rules forbid hard-coding, filtering or one-hot encoding the pipeline to the two training values and require a row for every test S1 entity, French ones included. block() partitions candidates by country but falls back to the full S2/S3 index for a label without counterpart (Chapter 6).

The pipeline reads every file through read_tsv() with sep="\t", dtype=str, keep_default_na=False and quoting=3 (no quote processing), so that a quote character inside a name or an empty address survives loading unchanged. 2.3 The evaluation metric

2.3.1 From Fβ to F0.5

For one S1 entity with predicted set h(e) and true set g(e), precision P is the fraction of predicted identifiers that are correct and recall R is the fraction of true identifiers that were predicted. The general Fβ score is the weighted harmonic mean of the two:

Fβ = (1 + β2) · P · R / (β2 · P + R), equivalently 1 / Fβ = (1 / (1 + β2)) · (1 / P) + (β2 / (1 + β2)) · (1 / R).

The parameter β expresses how many times more important recall is than precision. Setting β = 0.5 gives β2 = 0.25 and 1 + β2 = 1.25, hence the formula printed in the problem statement:

F0.5 = 1.25 · P · R / (0.25 · P + R).

In the harmonic-mean form the reciprocal of precision carries weight 0.8 and the reciprocal of recall weight 0.2. Along the diagonal P = R, ∂F0.5/∂P = 0.8 and ∂F0.5/∂R = 0.2, so a unit gain in precision is worth four times a unit gain in recall at a balanced operating point; the statement's "2×" phrasing refers to β = 1/2.

Substituting P = tp / m and R = tp / n, where tp is the number of correct identifiers, m = |h(e)| the number predicted and n = |g(e)| the number true, the per-entity score collapses to a form that makes the asymmetry concrete:

F0.5(e) = 1.25 · tp / (m + 0.25 · n).

Every wrong identifier adds a full unit to the denominator; every missed true identifier adds only a quarter. This is the single most important fact about the metric for the design of the decision layer.

2.3.2 Macro-averaging over S1 entities

The leaderboard score is the arithmetic mean of F0.5(e) over all S1 entities in the evaluation set. This is a macro average: an entity with twelve true matches and an entity with one contribute equally, and an entity with true matches none of which blocking paired with it contributes exactly zero however good the matcher is elsewhere (a singleton with no candidates, by contrast, scores 1.0 automatically). The pipeline reproduces the definition verbatim: f05() implements the per-entity score with its special cases, and macro_f05() averages it over the full key set tr1.entity_id, never over the subset that received predictions. The stdlib scorer utils/score.py implements the same function for independent checking (Chapter 10).

Micro-level statistics such as total true positives are therefore only diagnostics: ten extra true pairs on one heavily linked entity raise the score far less than ten zero-scoring entities turned into correct singletons.

2.3.3 The singleton rule

When g(e) is empty, precision and recall are undefined, and the challenge fixes the score by rule: an empty prediction earns 1.0 and any non-empty prediction earns 0.0. Two further degenerate cases score 0.0: an empty prediction when the truth is non-empty, and a non-empty prediction with no correct identifier. f05() checks these three cases in that order before evaluating the formula. The rule has no middle ground: on a singleton, one spurious identifier costs the entire point, and on a single-match entity one missing identifier costs the entire point too. Whether to emit the first identifier is therefore a symmetric decision; the precision bias comes from the second and later identifiers, since adding one wrong identifier to a correct single match drops the score from 1.000 to 0.556, whereas missing a second true identifier drops it only to 0.833. The optimal threshold is consequently a property of the data (singleton fraction, true-set sizes, classifier calibration), which is why main() sweeps thr over 0.20 to 0.95 in steps of 0.025 and the relative ratio over {0, 0.6, 0.7, 0.8, 0.9, 1.0} on out-of-fold probabilities instead of assuming 0.5.

2.4 Public and private leaderboards

A submission always covers the full test set. During the challenge the public leaderboard scores an undisclosed subset of the test S1 entities; after the deadline the private leaderboard scores the remaining entities and alone determines the final ranking. Two consequences follow. First, the public score is a noisy estimate of the private one, so decisions are driven by the out-of-fold macro F0.5 computed in main() on the training split, not by leaderboard probing. Second, the country mix of the two subsets is unknown, so the French share of the private set may differ from the public one; the per-country match-rate diagnostic printed at the end of main() exists to detect a French match rate that departs sharply from the US and Indian rates before submission (Chapter 10).

2.5 Constraints

No external lookup
External databases, entity-resolution APIs, government registries, geocoding services and internet-derived augmentation are prohibited on pain of disqualification. The pipeline reads only the seven TSV files located by find_data_dir(); its sole network action is the pip install rapidfuzz fallback on ImportError, which installs a library, not data (Chapter 13).
Model licence and size
The final model must carry an MIT or Apache-2.0 licence and have at most 8 billion parameters. The matcher is a LightGBM ensemble (MIT licence) whose parameters are split thresholds and leaf values: each cross-validation fold trains at most 2,000 rounds of 63-leaf trees (num_leaves=63) with early stopping after 100 rounds without improvement, and the final model is refitted for 1.1 times the mean best iteration of the folds. Even at the cap this is a few hundred thousand values, orders of magnitude below the limit.
Format validity
A submission that fails validation is not scored. The rules require exactly one row per test S1 entity, no duplicate rows, no duplicate identifiers within a list, S2/S3 prefixes only, and identifiers that exist in the test set. utils/validate_submission.py mirrors these checks locally and additionally rejects quote characters, empty or whitespace-padded list tokens, rows with other than two tab-separated columns, and, when --candidate is given, any matched identifier absent from the candidate list. It prints PASS and exits 0 only when no issue is found.
Open-set country
The country column must be treated as an unbounded set of string labels; France appears only at test time.
Reproducibility
The final package must regenerate both output files from the raw data using only the code under code/business_entity_resolution/ with pinned dependencies.

3 Data Understanding and Noise Taxonomy

This chapter describes the input data as the pipeline sees it: three tab-separated sources whose records share no key, an entity_id prefix that is the only source indicator, and free-text names and addresses in which the same business is spelled, abbreviated, truncated and reordered differently in every source. The noise patterns of the problem statement are expanded into a systematic taxonomy that pairs each pattern with the mechanism in er_pipeline.py that absorbs it. The chapter also sets out the address anatomy of the three countries, the open-set country rule, and the profiling output that must be inspected before any modelling decision is trusted.

3.1 Sources and What Each Contributes

3.1.1 The three sources

Every split (train and test) consists of three files, *_source1.tsv, *_source2.tsv and *_source3.tsv, with identical columns: entity_id, business_name, business_address and country. The problem statement designates Source 1 (S1) as the deduplicated reference source: each S1 record stands for exactly one real-world business, and no two S1 records stand for the same business. Sources 2 and 3 (S2, S3) are independent feeds carrying partial, noisy fragments of the same businesses; the task is to attach each S2/S3 record to the S1 entity it describes, or to leave an S1 entity as a singleton when neither feed mentions it. Because S1 is deduplicated, an S2/S3 record can belong to at most one S1 entity, a fact the decision layer exploits (see Chapter 9), whereas an S1 entity can own zero, one or many S2/S3 records.

The training split adds train_ground_truth.tsv, which maps each S1 source1_entity_id to a comma-separated matched_entity_ids list that is empty for singletons. load_split() parses it into a dictionary from S1 id to a set of matched ids; the empty string yields an empty set, so singletons are represented explicitly. The same function concatenates S2 and S3 into a single frame, because blocking and matching treat the two feeds as one candidate pool and recover the source distinction from the id prefix.

3.1.2 entity_id prefix semantics

There is no source column. A record's origin is encoded in the first two characters of its entity_id: S1-, S2- or S3-. prep() materialises this as the src column (entity_id.str[:2]), from which features() derives the binary feature is_s3 and decode_table() forms its per-(S1, source) groups. The prefix also carries two hard output constraints of Chapter 2: a matched id must begin with S2- or S3- and must exist in the test set. Because the pipeline only emits ids read from the test S2/S3 files, both hold by construction (see Chapter 11).

3.1.3 Loading discipline

The files are tab-separated because addresses and id lists contain commas. read_tsv() reads with sep="\t", dtype=str (postal codes must keep leading zeros), keep_default_na=False (an empty address is an empty string, not NaN) and quoting=3 (csv.QUOTE_NONE, so a stray double quote inside a name does not swallow the rest of the line). Reading without these settings corrupts the data silently.

3.3 Noise Taxonomy

The problem statement lists the noise families informally. Two details of _addr_nums() follow from this anatomy. First, the postal code is removed from the digit-run set so that two US records in the same ZIP do not appear to share a street number; num_overlap and num_conflict would otherwise be polluted by the most widely shared number in the data. Second, the removal is suppressed when the postal match is the leading number and does not end the string, because a 5-digit US house number with the ZIP omitted also matches _postal and must remain available as the house number. Both rules are precision measures: a spurious numeric agreement is exactly the evidence that pushes a non-match over the threshold.

A related consequence of token-level expansion is that expand() has no notion of position. The US state codes CT, FL and NE are rewritten by ADDR_ABBR to court, floor and northeast wherever they occur, and an Indian Sec 5 becomes sector 5 even when it abbreviates something else. These rewrites are consistent: both records of a true pair receive the same expansion, so pair similarity is unaffected, and a token shared by every record in a state carries little TF-IDF weight. The cost is confined to the rare non-pair in which an expansion manufactures a shared token.

The Indian anatomy is the hardest. The same building can be written 12/3, No. 12/3, 12-3 or Door 3, Plot 12; after basic() all four yield the digit set {12, 3}, but only the first three yield house = 12, so house_state can report a false disagreement while num_overlap reports full agreement. The classifier sees both signals and learns which to trust (see Chapter 8). City-name transliterations (Bangalore versus Bengaluru) are deliberately not mapped: a gazetteer would be an external resource, and the same-postal blocking view already places both spellings in one block whenever the PIN is present.

3.5 The Open-Set Country Requirement

The training data cover US and India; the test data additionally contain France, which appears in no training record. The statement forbids hard-coding, filtering or one-hot-encoding the country to the training set, and requires every test S1 entity, French ones included, to appear in the output. The pipeline complies in three ways. The country value is never a feature: features() derives no column from it, so the model cannot learn a rule that France violates. The value is used only as a partition key in block(), where country_n = basic(country) is compared as a plain string; any label, including an unseen or blank one, forms its own group. Finally, when an S1 group's label does not occur among the S2/S3 records, block() compares that group against every S2/S3 record instead of an empty block, so a spelling variant such as USA against US, or a missing label, degrades to slower blocking rather than to a silently dropped entity.

Risk: unseen-country drift. Compliance with the rule does not remove the statistical problem. The classifier and the decision parameters (thr, ratio) are fitted on US and Indian pairs only (see Chapters 8 and 9). French names carry longer legal forms and articles, French addresses put the postal code before the commune, and the TF-IDF vocabulary for French text is learned only at test time when the vectorisers are refitted. The similarity distribution of true French pairs may therefore sit above or below what the tuned threshold assumes. Under F0.5 the consequence is asymmetric: a threshold too low for France produces false merges on French singletons at a cost of 1.0 each, whereas a threshold too high loses only part of a point per missed match. The only in-pipeline guard is the per-country match rate printed at the end of main(); a French rate far above the seen countries' is the signature of over-matching. Chapter 14 discusses a pseudo-unseen-country validation (train on US, validate on India) that would quantify the gap.

4 System Architecture Overview

This chapter describes the solution as a software system: its architectural style, the modules of er_pipeline.py and the responsibility of each function, the data contracts between stages, the control flow of main() for the training and test splits, the runtime environment with its dependencies and licences, the logging design, and the configuration surface. Chapters 5 to 11 go deeper into each stage; this chapter fixes the vocabulary and interfaces they rely on.

4.1 Architectural style

The system is a single-process batch pipeline: one Python module, er_pipeline.py, with one entry point, main(), that starts from the raw TSV files and ends with the two submission files. There are no services, no state between runs and no intermediate files. The organising principle is a chain of pure functions over two in-memory containers: pandas DataFrames for record-level and pair-level tables, and SciPy compressed-sparse-row (CSR) matrices for the TF-IDF (term frequency–inverse document frequency) representations used in blocking. Each stage takes frames in and returns a new frame out: prep() copies its input before adding columns, block() and features() build fresh frames, and decode_table() copies only the three columns it needs. No function mutates module-level state; the only globals are the lookup tables (NAME_ABBR, LEGAL, ADDR_ABBR, ADDR_STOP), the compiled regular expressions and the start timestamp T0 that log() reads.

Three considerations tie this style to the evaluation. First, the metric is a macro-average of per-entity F0.5 with an all-or-nothing rule for singletons (see Chapter 2), so the decision parameters must be tuned on out-of-fold predictions computed from exactly the features the test path will see; a single linear flow guarantees this because both splits pass through the identical prep() → block() → features() sequence and the column list feats is derived once and reused. Second, the corpus is expected to fit in the memory of a Kaggle CPU kernel, so a scheduler or checkpointing layer would add failure modes without capability; the one memory-sensitive operation, the dense chunk inside topk_sparse(), is bounded by construction (see Chapter 12). Third, the fair-play rules require a reviewer to verify that no external lookup occurs, and a single file whose only network action is an optional pip install rapidfuzz fallback is the easiest artefact to audit (see Chapter 13).

A convention that runs through every stage is positional row identity. After prep() resets the index, every record is addressed by its integer position; candidate, feature and decode rows carry the pair (i1, i2), where i1 indexes the S1 frame and i2 the concatenated S2+S3 frame, and entity identifiers are re-attached only at the edges: by to_lists() on output and by the labelling and recall-diagnostic lines of main(), which index tr1.entity_id.values and tr2.entity_id.values by position. This keeps the look-ups in features() and the group-by operations unambiguous and lets GroupKFold group by i1 so that all candidates of one S1 entity fall into the same fold (see Chapter 10).

4.4 Control flow of main()

Figure 4.2 shows the two paths main() executes in sequence. Both splits are loaded and profiled first, so a missing test file fails before any training time is spent.

On the training path the label y of a candidate pair is 1 when the S2/S3 identifier belongs to the ground-truth set of the S1 identifier and 0 otherwise; pairs that blocking never produces are neither positives nor negatives and appear only in the recall diagnostics. GroupKFold(args.folds) with groups=ftr.i1 yields out-of-fold (OOF) probabilities: a probability for every training pair from a model that never saw that pair's S1 entity. The decision parameters are chosen by exhaustive search on the OOF probabilities, and the final model is refit on all pairs with 1.1 times the mean early-stopped iteration count.

On the test path no label is read. block() refits its vectorisers on the test texts, so the n-gram vocabulary of the unseen country is learned from the test records themselves. Matches and the full candidate frame are converted to identifier lists and written in the same loop, so the matches are a subset of the candidates by construction.

Design note. The frame fte that feeds model.predict() is the one written as candidate_pairs.tsv, so the file documents the exact set the model scored, as the organisers define it.

5 Text Normalisation Layer

This chapter specifies the normalisation layer implemented by prep() in er_pipeline.py: the deterministic rewriting of every raw business_name, business_address and country value into the canonical columns that blocking (see Chapter 6) and pair feature engineering (see Chapter 7) consume. basic() operates on characters, expand() on tokens against four fixed vocabularies (NAME_ABBR, LEGAL, ADDR_ABBR, ADDR_STOP), and a final tier extracts structured signals that survive text noise: alias variants, postal code, street numbers and house number. Every rule exists to make two spellings of the same business collide while leaving genuine differences visible, the balance the precision-weighted F0.5 metric demands.

5.1 Role of Normalisation in a Precision-Weighted Pipeline

Normalisation is applied identically to Source 1 (S1) and to the concatenated Source 2/3 (S2/S3) frames, on both splits, before any comparison is made. The core name without legal forms drives the TF-IDF blocking views and most name similarities; the full normalised name keeps the legal form so the matcher can still see that acme incorporated and acme llc disagree on a token that sometimes separates two businesses. Under F0.5 an over-aggressive canonical form raises blocking recall but hides evidence of a false merge, which on a singleton costs a full point (see Chapter 2); the layer therefore canonicalises for recall in the blocking columns and preserves residual detail in parallel columns for precision. All tables are static literals in the source; no geocoder, gazetteer or registry is consulted (see Chapter 13).

5.2 Character Tier: basic()

basic(s) is the entry point for every text field, including the country label. It applies five operations in a fixed order; the order is load-bearing, as the dotted-acronym rule must run before punctuation is destroyed.

  1. Unicode folding. unicodedata.normalize("NFKD", str(s)) decomposes precomposed characters into base letter plus combining mark and maps compatibility forms (full-width Latin, ligatures) to canonical equivalents; .encode("ascii", "ignore").decode() discards every non-ASCII code point, so accents vanish (Société → Societe); the result is lower-cased.
  2. Symbol words. & becomes and and @ becomes at , so A&B Traders and A and B Traders share a token stream.
  3. Dotted acronyms. _dotted collapses u.s.a into usa and p.v.t. into pvt (Section 5.2.1).
  4. Punctuation stripping. _punct = [^a-z0-9 ]+ replaces every run of characters outside lower-case letters, digits and space with one space, so commas, hyphens, apostrophes, slashes and remaining dots become separators.
  5. Whitespace. _space = \s+ collapses runs; the result is stripped.

5.2.1 The _dotted regex

_dotted = (?<![a-z])(?:[a-z]\.){2,}[a-z]?(?![a-z])
(?<![a-z])
Negative look-behind: the match may not start right after a letter, so the tail of an ordinary word is never mistaken for an acronym (abs.c.d is left alone).
(?:[a-z]\.){2,}
At least two letter-dot units, the signature of a dotted acronym; a single unit such as no. or bros. does not qualify and falls through to the punctuation rule.
[a-z]?
An optional final letter without its dot, so that u.s.a (no trailing dot) is captured whole rather than leaving a dangling a.
(?![a-z])
Negative look-ahead: the acronym must end at a non-letter. In a.b.cdef the optional letter cannot be consumed, no match occurs, and the string degrades harmlessly to a b cdef.

The replacement removes the dots inside the matched span only: u.s.a → usa, l.l.c. → llc, m.g. rd → mg rd. Without this step the punctuation rule would produce p v t, three single-letter tokens that never hit the pvt → private expansion or the LEGAL filter and add spurious word boundaries to the n-gram vectors; collapsing them first lets P.V.T. Ltd., Pvt Ltd and Private Limited converge on one core name.

5.4 Name Columns: norm_name(), core_name() and name_parts()

norm_name(s) is expand(basic(s), NAME_ABBR). core_name(n) removes every token in LEGAL and, if nothing remains (The Company), returns the full normalised name instead: an empty core name would yield an all-zero TF-IDF row in the name blocking view, a name-blind row in the full view and zero for every name similarity, leaving the address alone to find and confirm a match.

5.4.1 The _ALIAS regex and why it runs on the raw string

_ALIAS = \b(?:d\s*/\s*b\s*/\s*a | d\.b\.a\.? | dba | doing business as | trading as
          | t\s*/\s*a | a\s*/\s*k\s*/\s*a | a\.k\.a\.? | also known as
          | formerly(?: known as)?)\b        (flag re.I; spaces added for reading)

Each alternative is a marker separating a legal name from a trade name inside one field: the d/b/a family (optional spaces around the slashes, dotted d.b.a with an optional final dot, bare dba, doing business as), the British trading as and t/a, the a/k/a family with also known as, and formerly with or without known as. The \b anchors require a whole word, so t/a does not fire inside Fast/Auto; re.I accepts DBA. Bare aka is deliberately absent: it occurs as a legitimate name element (personal, place and brand names), and a false split would set has_alias and invent a second variant for an entity that has none.

The regex runs on the raw field because basic() is destructive: it turns d/b/a and t/a into d b a and t a, sequences indistinguishable from initials, and _dotted collapses a.k.a. into aka, precisely the bare token the regex refuses to match. Splitting first is the only order in which the marker is still recognisable.

name_parts(raw) splits on _ALIAS, applies core_name(norm_name(·)) to each piece, discards empty pieces and falls back to the single core name when nothing survives; the result is name_alts. In prep() the main column name_n is built from the joined pieces (" ".join(_ALIAS.split(s))): legal and trade names are concatenated with the marker removed, so blocking sees both vocabularies in one string and keeps its recall, while n_alias_best in Chapter 7 scores every (variant, variant) pair to reward a record that matches either name alone.

5.5 Address Columns: norm_addr(), _postal and _addr_nums()

norm_addr(s) is expand(basic(s), ADDR_ABBR) and yields addr_n; removing ADDR_STOP tokens yields addr_c, used by the blocking views and the address similarities.

5.5.1 The _postal regex

_postal = \b(\d{5,6})(?:-\d{4})?\b

The capture group requires a run of exactly five or six digits bounded by word boundaries; an optional -dddd suffix is consumed but not captured. prep() applies it to the raw address and keeps the last match, because postal codes conventionally close an address whereas plot and house numbers open it. A US ZIP or ZIP+4 (62704-1234) yields 62704; the six-digit Indian PIN (201301) is captured because \d{5,6} is greedy; the five-digit French code postal (75002), which precedes the city name, is captured by the same rule, so the unseen country needs no special case. Runs of seven or more digits (phone numbers) never match, because a word boundary cannot fall inside a digit run. A missing code yields the empty string, which the feature layer encodes as an explicit unknown state rather than a disagreement.

5.5.2 _addr_nums(): digit runs and the house number

_addr_nums(a, p) takes the normalised address and the postal code. It collects every digit run with _digits = \d+, removes the last occurrence of the postal code, and returns the frozenset of remaining runs (nums) together with the first remaining run (house); an address whose only digit run is its postal code therefore has an empty house. The removal is guarded by one exact exception:

if p and p in ns and (ns[0] != p or a.endswith(p)):
    drop the last occurrence of p from ns

The postal code is removed when it is not the leading number, or when it is the leading number but the address also ends with it. The case that is not removed is a five- or six-digit run that opens the address and does not close it: a US house number such as 12345 Main Street on a record whose ZIP is missing. _postal captures that house number as the postal code, and without the guard it would vanish from nums, leaving the record without its most discriminative address token. The guard keeps it as house and in nums, so house_state and num_overlap in Chapter 7 still fire. Under F0.5 these numeric agreements are the cheapest precision signal available: two records sharing a name but conflicting on a house number are far more often neighbouring branches than one business.

Risk. In the exception case the postal column still holds the house number, so postal_state compares it against the other record's real ZIP and reports -1. Likewise the +4 suffix of a ZIP+4 stays in nums as a separate run (1234 in the worked example), so a pair where only one side carries the suffix loses some num_overlap. Both effects are systematic and visible to the tree model, but they mark where a rule-based extractor is weaker than a country-aware parser (see Chapter 14).

6 Candidate Generation (Blocking)

This chapter describes the candidate-generation stage implemented by block(), topk_sparse() and pair_cos(). Blocking replaces the infeasible cross product of Source 1 against Source 2 and Source 3 with a short list of plausible partners per Source 1 record and thereby fixes the recall ceiling of the system. It combines three character n-gram TF-IDF views with an exact-key postal view, partitions by country with an open-set fallback, bounds memory by construction, and, together with the training-side checks in main(), prints diagnostics that show where to act when the ceiling is too low.

6.1 Why blocking is needed

The matcher of Chapter 8 scores one pair at a time. Without pre-selection it would score every Source 1 (S1) record against every Source 2 or Source 3 (S2/S3) record, |S1| × |S2+S3| pairs: with, for instance, a few hundred thousand records per side that is 1010 to 1011 pairs, infeasible for the string-alignment features of Chapter 7 and hopelessly imbalanced for the classifier. Blocking restricts the comparison space to pairs that share cheap evidence of similarity.

Blocking also caps the score. A true partner absent from the candidates of its S1 record can never be predicted; the fraction of ground-truth pairs that survive is the recall ceiling. Under the macro-averaged F0.5 of Chapter 2 the ceiling bites per entity: an S1 entity with true matches, none of which is blocked, contributes exactly 0.0 whatever the matcher does, while a singleton is unaffected. The stage is therefore designed for recall and leaves precision to the matcher and the decision layer of Chapter 9. The table returned by block() is also, unfiltered, the content of candidate_pairs.tsv, which must be exactly the set the model runs inference over.

6.2 Representation: character n-gram TF-IDF

Each view is a TfidfVectorizer with analyzer="char_wb", ngram_range=(2, 4), min_df=2, sublinear_tf=True and dtype=np.float32. The char_wb analyser pads each token with a space and emits its character 2-, 3- and 4-grams without crossing token boundaries, so a typo or transposition changes a handful of n-grams and leaves the rest intact, which tolerates the residual noise the tables of Chapter 5 do not cover. min_df=2 drops n-grams found in a single document, which can never contribute to a dot product between two records, so the vocabulary shrinks at no cost to recall. sublinear_tf replaces the term frequency tf by 1 + log(tf), so a long address repeating a common n-gram does not dominate its own vector, and float32 halves the memory of the matrices and of the dense chunks of 6.5.

The vectoriser is fitted on pd.concat([a, b]), the S1 and S2/S3 texts of the split being processed. Rows are L2-normalised (the default), hence the dot product of two rows is their cosine and one sparse product yields all cosines. Refitting on the test split learns French n-grams from the test records themselves, with no external vocabulary (see Chapter 13).

6.3 The four views

block() builds three fuzzy views and one exact-key view (Table 6.1). Each fuzzy view vectorises a different text: the core name name_c, the concatenation name_c + " | " + addr_c, and the cleaned address addr_c (Chapter 5). The views are complementary with respect to the noise taxonomy of Chapter 3: the name view finds partners whose address is missing or rewritten; the address view finds partners whose name is a trade name, acronym or heavy abbreviation; the full view ranks highest the pairs on which both fields agree, and its cosine cos_full later drives the rank and gap features of Chapter 7. Depth differs per view: k = 25 for name and full, because near-duplicate names (chain branches, common words) are frequent and the true branch must stay in the list; k = 10 for address, because addresses are shared by many businesses and an address-only neighbour is weak evidence.

The fourth view is exact-key. Within a country block, S2/S3 records are grouped by their extracted postal code; for every S1 postal group with a matching S2/S3 group, the name-view vectors of the two groups are compared and the top kpostal = 10 by name cosine are kept (empty codes are skipped). This recovers matches whose name is too noisy for the country-wide top 25: inside one ZIP or PIN group the competition is the postal group rather than the whole country, so the same name cosine is far more discriminative. The view is silent for records whose address carries no 5- or 6-digit code (postal is then empty, Chapter 5), so it complements the fuzzy views rather than replacing them.

6.4 Partitioning by country and the open-set fallback

The country label is the only field that permits an exact partition. block() iterates over s1.groupby("country_n"), where country_n is basic(country), and restricts the S2/S3 index i2 to rows with the identical normalised country. Partitioning makes a fixed k more valuable, since the top 25 within one country are likelier to contain the true partner than the top 25 across three, and it reduces the product cost to Σc |S1c| × |S2S3c|.

The label is an open set, as the problem statement requires. other_countries is computed from the S2/S3 side; if an S1 group's label is absent from it, the group is compared against all S2/S3 rows rather than an empty block, so no S1 entity is silently dropped when its label is unseen, blank or misspelt on one side. France is unseen in training but present in the test set, so wherever the French label occurs on the S2/S3 side, French S1 records block within that block exactly as US and Indian records do; were the label present only on the S1 side, the fallback would compare those records against every S2/S3 row. Nothing in the code enumerates countries, and the same block() call is made for the training and the test split.

Risk. If a blank label occurs on both sides, blank S1 records are compared with blank S2/S3 records only, which is too narrow if blanks are noise rather than a category. The per-country recall diagnostic of 6.8 exposes this; the remedy is to route the blank group through the all-records path.

6.5 Bounded top-k retrieval: topk_sparse()

Retrieving the k nearest S2/S3 rows for every S1 row of a view is a sparse product of the S1 matrix A with the transposed S2/S3 matrix BT, followed by a row-wise selection. To avoid materialising the full |A| × |B| product, topk_sparse() processes A in row chunks sized from |B|: chunk = max(16, int(max_cells // n_b)) with max_cells = 2e7. The dense transient S = (A[i:i+chunk] @ BT).toarray() then holds about 2 × 107 float32 cells whatever the block size, until |B| exceeds 1.25 × 106 rows: from there the floor of 16 rows keeps the loop efficient at the price of a proportionally larger transient (Table 6.2). Before the loop, k is clipped to |B| and an empty A or B returns empty arrays of width 0, so a tiny country block cannot raise.

Selection uses np.argpartition(S, S.shape[1] - k, axis=1): partitioning at kth = |B| − k places the k largest scores of each row in the last k positions, unordered, at linear expected cost, without a full sort or a negated copy of S. The slice [:, -k:] is followed by .copy(), and the copy matters: argpartition returns a full chunk × |B| int64 array, and a slice of it is a view that keeps the whole array alive; appending views to idx_out would retain every full-width array until the function returns, multiplying peak memory by the number of chunks. np.take_along_axis gathers the scores, and the stacked arrays are returned.

Because argpartition always returns exactly k columns, a row with fewer than k records sharing any n-gram is padded with arbitrary zero-score columns. The cut keep = sc > 0.05 removes this padding and near-zero neighbours. Each view's survivors are mapped to global indices (np.repeat(i1, k) for rows, i2[idx] for columns), stacked, and de-duplicated with drop_duplicates(), since a good pair is usually found by several views; an S1 record has at most 25 + 25 + 10 + 10 = 70 candidates before de-duplication.

6.6 Memory budget and time complexity

Three transients are allocated per chunk: the dense float32 scores at 4 bytes per cell, the int64 argpartition result at 8 bytes per cell, and the sparse product before toarray(), at 4 bytes of data plus 4 bytes of column index per non-zero. The sparse product is often close to dense (frequent bigrams occur in most records) and is budgeted at up to 8 bytes per cell. They are not all alive at once: the sparse product is released as soon as toarray() returns, before argpartition allocates, so the true peak is the larger of (sparse product + scores) and (scores + argpartition), and the sum of all three is a conservative bound. 6.7 Cosines for every surviving pair: pair_cos()

A pair retrieved only by the address view carries no name score from retrieval, yet the matcher needs all three cosines for every pair. block() therefore calls pair_cos(A, B, i1, i2) once per fuzzy view after the union. The function gathers A[i1] and B[i2] in slices of 200,000 pairs, multiplies them element-wise with the sparse multiply() and sums each row, which for L2-normalised rows is the cosine; slicing bounds memory regardless of the pair count. The resulting cos_name, cos_full and cos_addr are the first features of Chapter 7, and a uniformly computed cos_full is what makes the rank and gap features comparable.

7 Pair Feature Engineering

This chapter describes features(), which turns every candidate pair from blocking (Chapter 6) into the 38-column numeric row scored by the LightGBM matcher of Chapter 8. The features fall into three groups: pairwise similarities of the normalised name and address, agreement states of the structured address components, and context features that place a pair among the competing candidates of the same Source 1 and Source 2/3 record. Each similarity absorbs one noise class from Chapter 3; the context features let a per-pair classifier approximate the per-entity decision that precision-weighted F0.5 rewards.

7.2 TF-IDF cosines

The three cosines are not recomputed by features(); block() attaches them through pair_cos() for every surviving pair, whichever view retrieved it. Each view has its own TfidfVectorizer(analyzer="char_wb", ngram_range=(2, 4), min_df=2, sublinear_tf=True) fitted on the union of both sides, so a cosine is corpus-weighted (the inverse document frequency of the n-grams of "road" or "nagar" is low), which complements the rapidfuzz scorers that weight every character equally. cos_full is the basis of the rank and gap features of 7.7 because it is the only score combining name and address evidence for every pair.

7.3 rapidfuzz name similarities

7.3.1 What each scorer computes

All five scorers run on the core name name_c (Chapter 5). fuzz.ratio is the normalised Indel similarity: with LCS the length of the longest common subsequence, ratio = 200·LCS / (|a| + |b|). It is order-sensitive and treats every character alike; each other scorer relaxes it in one direction.

fuzz.token_sort_ratio sorts the whitespace tokens of both strings, re-joins them and applies ratio, so any permutation of the same tokens scores 100: it absorbs reordering and nothing else. fuzz.token_set_ratio forms the sorted intersection t0 of the token sets and the strings t0 + (tokens only in a) and t0 + (tokens only in b), and returns the best ratio among the three pairings; when one token set is a subset of the other the score is 100, so extra tokens on one side are ignored wherever they occur. fuzz.partial_ratio returns the best ratio of the shorter string against any window of its own length in the longer one; it absorbs truncation but not interleaved extra tokens. JaroWinkler.similarity counts characters that match within a window of ⌊max(|a|,|b|)/2⌋ − 1 positions, penalises transpositions and adds a prefix bonus of up to four characters with weight 0.1, JW = J + ℓ·0.1·(1 − J); it stays high for an interior typo when the first characters agree and drops fast when they differ.

All five are kept because their disagreement pattern is itself a signal: n_tset = 100 with n_ratio = 55 is a subset relation, 100 with 100 an exact match. n_full_ratio applies fuzz.ratio to the full name name_n, the only feature that still sees the legal form; it separates records whose core names coincide but whose legal forms differ, often the line between a match and a costly false positive.

7.4 Alias and acronym features

Chapter 5 splits a raw name on the explicit alias markers of the _ALIAS regex (dba, d/b/a, doing business as, trading as, t/a, a.k.a., also known as, formerly known as; a bare aka is excluded because it can be a genuine name token) into the list name_alts of core-normalised variants, while name_c keeps the concatenation with the markers removed. n_alias_best is the maximum token_sort_ratio over every variant of L paired with every variant of R, so "Acme Holdings LLC dba Acme Pizza" scores 100 against "Acme Pizza" although the concatenated core name "acme holdings acme pizza" scores lower on n_ratio and n_tsort (n_tset and n_partial already reach 100 through the subset relation). has_alias flags pairs where either side has more than one variant; on every other pair n_alias_best equals n_tsort, so the flag tells the model when the alias score carries new information.

n_acronym covers the opposite direction: one side is a single token equal to the initials of the other, multi-token side. Because core_name() already drops "of", "and" and "the", the initials of "state bank of india" are "sbi", the token a second source is likely to store. The feature is symmetric and, when it fires, carries information no character scorer does: "sbi" against "state bank india" scores about 32 on n_ratio and no better than 50 on n_partial.

Risk. n_tset, n_partial and n_acronym reward subset relations, which chain branches also share ("acme pizza" against "acme pizza airport"). They buy recall on trade names at a price in precision; the address states of 7.5 and the context features of 7.7 are the counterweight, and Chapter 9 sets the operating point on the measured F0.5.

7.5 Address features

Four scorers run on the cleaned address addr_c: a_ratio, a_tset, a_partial and a_jacc. Addresses carry more benign extra tokens than names (district or state names survive stop-word removal), so a_tset matters more here and is the address score used for the gap features.

The structured components yield agreement states rather than similarities. postal_state is ternary: 0 when either postal code is missing, 1 when both are present and equal, -1 when both are present and differ. The states are kept apart because a missing code is absence of information whereas a conflict is evidence against a match, which F0.5 makes valuable. house_state applies the same encoding to the leading digit run house. num_overlap is the Jaccard of the digit-run sets nums (_addr_nums() removes the postal code unless it is also the leading number of the address, the case of a five-digit US house number with the ZIP missing), with the sentinel -1 when either side has no digits, so "nothing to compare" is distinct from "numbers present, none shared"; num_conflict makes the latter an explicit boolean.

7.6 Lengths and source flag

len_l, len_r, alen_l and alen_r are the character lengths of core name and cleaned address on each side. A ratio of 80 on two 6-character names is one typo; on two 40-character names it is several, so the lengths let the model condition every similarity on the amount of text behind it. is_s3 is 1 when the right record comes from Source 3 (src is the two-letter prefix of entity_id); it lets the model learn source-specific field quality, and decode_table() reuses the same column to group candidates per (S1, source).

7.7 Context features

Every feature so far is a function of the pair alone, but the metric is computed per Source 1 entity, and the question is not "is this pair similar" but "is this the right partner, given the alternatives". The context block gives the pairwise model that view through pandas group operations over the candidate table:

for col in ["cos_full", "n_tset", "a_tset"]:
    f[f"{col}_gap1"] = f[col] - f.groupby("i1")[col].transform("max")
    f[f"{col}_gap2"] = f[col] - f.groupby("i2")[col].transform("max")
f["rank1"] = f.groupby("i1")["cos_full"].rank(ascending=False, method="first")
f["rank2"] = f.groupby("i2")["cos_full"].rank(ascending=False, method="first")
f["n_cand1"] = f.groupby("i1")["i2"].transform("size")
f["n_cand2"] = f.groupby("i2")["i1"].transform("size")

For each of the three scores, _gap1 is the pair value minus the best value among all candidates of the same S1 record, and _gap2 the same relative to all S1 records competing for the same S2/S3 record; both are 0 for the leader and negative otherwise. rank1 and rank2 are the positions by cos_full on the two sides (1 = best; method="first" breaks ties by table order, so ranks are integers), and n_cand1, n_cand2 are the group sizes. Design note. The three gap bases cover independent axes: cos_full for joint evidence, n_tset for the most permissive name score, a_tset for the most permissive address score. A pair leading on the address but trailing on the name is the signature of a co-located different business. Ranks and counts use cos_full only, since one ordering suffices for position.

7.8 Leakage, categorical handling and value encoding

The context features are computed once on the complete candidate table of a split, before the GroupKFold of Chapter 8 is drawn. Groups by i1 are fold-internal, since every candidate of an S1 record shares its fold; groups by i2 cross folds, because the competitors of an S2/S3 record may be S1 records held out elsewhere. This is not label leakage: the group statistics use only unsupervised scores and counts, never y, and the identical computation is available at test time because features() runs on the complete test table. What would be leakage, and is absent, is any group aggregate of the label such as a target encoding of i2.

No column is declared categorical. postal_state and house_state are integers in {-1, 0, 1}; two numeric splits (below -0.5, above 0.5) isolate each state, so numeric handling is lossless. The country is intentionally not a feature: the test holds a country absent from training (Chapter 3), and a country column would invite splits that cannot transfer. No feature yields a missing value: jacc() returns 0.0 for empty sets and num_overlap uses the -1 sentinel. The layer costs nine fixed rapidfuzz calls per pair (six on names, three on addresses) plus |L.name_alts| × |R.name_alts| token_sort_ratio calls for n_alias_best; it is expected to be the largest CPU cost of the pipeline, to be confirmed from the run log timings of Chapter 12. 8 Matching Model: LightGBM Classifier

This chapter describes the supervised matcher that turns the 38-column feature row of Chapter 7 into a match probability for every candidate pair: a single LightGBM gradient-boosted tree ensemble with a binary log-loss objective, trained inside main() on the blocked training pairs, validated with a five-fold GroupKFold grouped by Source 1 record, and refitted on all pairs before scoring the test set. The model never decides anything itself; it emits calibrated probabilities, and every decision the precision-weighted F0.5 metric depends on is deferred to the threshold and relative-ratio rule of Chapter 9. The chapter covers the choice of trees, the hyperparameters, label construction, grouped out-of-fold (OOF) validation, early stopping and refit, gain importances, and the interface a replacement model must honour.

8.1 Why gradient-boosted trees for pairwise entity resolution

A pairwise matcher receives one row per (S1, S2/S3) candidate pair and outputs the probability that the two records describe the same business. The feature row of Chapter 7 is heterogeneous by design: rapidfuzz scores on 0-100, TF-IDF cosines on 0-1, Jaccard indices, character lengths, integer ranks and counts, binary flags such as n_acronym, and ternary agreement states (postal_state, house_state) whose values 1, 0 and −1 mean "agree", "unknown" and "conflict". A gradient-boosted decision tree (GBDT) ensemble consumes such a mix without scaling, one-hot encoding or imputation, because every split is a threshold on one raw column.

The decisions that matter for the metric are interactions, not marginal effects. A moderate name score (n_tset around 70) is strong evidence when postal_state = 1 and num_conflict = 0, and weak evidence when postal_state = −1; a negative cos_full_gap1 changes the meaning of every absolute similarity, since a pair dominated by a competitor of the same S1 record is far more often a near-duplicate of a different business than a second true record. Trees express such conditional rules natively; a linear model needs hand-built cross terms. Because F0.5 weights precision twice as heavily as recall and a singleton scores 1.0 only with an empty prediction (see Chapter 2), the matcher must separate "similar but wrong" from "similar and right", a separation carried by conflicts and context interactions.

The remaining reasons are practical. Positives are a small minority of the blocked pairs (the measured rate is recorded in Table 8.3), so a model that converges in a few hundred trees on CPU (n_jobs=-1) is preferable to one needing GPU epochs. LightGBM is MIT-licensed, and at most 2,000 trees of 63 leaves amount to on the order of 105 split thresholds and leaf values, negligible against the 8B parameter cap (see Chapter 13). Its per-feature gain also keeps the feature layer auditable when a rule of Chapter 5 changes.

8.3 Label construction and class balance

Labels exist only for the training split and come from the ground truth loaded by load_split(), which maps each S1 entity_id to its set of matched S2/S3 ids. After blocking and feature computation, main() sets y = 1 for a candidate row if and only if the S2/S3 id belongs to the ground-truth set of its S1 id:

ftr["y"] = [int(id2[b] in gt.get(id1[a], ()))
            for a, b in zip(ftr.i1.values, ftr.i2.values)]

Two consequences follow. The model is trained only on pairs that blocking produced: a true pair no view retrieved is neither positive nor negative, and its loss is charged to the blocking recall ceiling of Chapter 6. And the negatives are the hard negatives blocking found plausible, exactly the distribution met at test time.

The classes are imbalanced: block() can attach up to 25 + 25 + 10 + 10 = 70 candidates to one S1 record before de-duplication (the union of four top-k views, Chapter 6), whereas the ground truth lists zero, one or a few matches per record, so positives are a small minority; the exact positive rate is a run-log quantity (Table 8.3). The pipeline deliberately applies no reweighting, neither is_unbalance, scale_pos_weight nor sample weights. Reweighting shifts the probability scale, and the decision layer of Chapter 9 never uses 0.5 as a boundary; it sweeps the absolute threshold from 0.20 to 0.95 and a relative ratio directly on the OOF macro F0.5. What the sweep needs is a well-ordered, calibrated probability, which unweighted log-loss provides; reweighting would instead inflate probabilities on ambiguous pairs, the opposite of what a precision-weighted metric with an all-or-nothing singleton term rewards.

8.4 Grouped cross-validation and out-of-fold assembly

The held-out probabilities estimate the leaderboard score and are the data on which the threshold and ratio are selected, so validation rows must come from S1 records the model never saw. A plain random split violates this: the candidates of one S1 record would be scattered across folds, so the model would predict one of them having learned the others. The context features of Chapter 7 make the leak worse, since cos_full_gap1, rank1 and n_cand1 encode the whole candidate set of a record.

main() therefore uses GroupKFold(args.folds), five folds by default, with groups=ftr.i1: every candidate of an S1 record, and hence every positive and negative competing for it, lands in the same fold. Because the decode of Chapter 9 operates per S1 record, the fold structure also makes the OOF macro F0.5 a proper per-entity estimate, including singleton records, which contribute only negatives and are the entities most exposed to a false positive. Figure 8.1 shows the mechanism.

Each fold calls lgb.train() with a training lgb.Dataset on ftr.iloc[a][feats] and a validation set on ftr.iloc[b][feats]. The held-out slice is scored with m.predict(..., num_iteration=m.best_iteration) and written into oof[b]; the five index sets b partition the rows, so oof ends as a full-length vector aligned with ftr, which decode_table() consumes. Context features grouped by i2 (cos_full_gap2, rank2, n_cand2) do span folds, but they derive from unsupervised similarities only and carry no label information.

8.5 Early stopping, best iteration and the refit

Each fold trains for at most 2,000 boosting rounds under lgb.early_stopping(100, verbose=False), which monitors the validation binary log-loss and halts once it has not improved for 100 consecutive rounds; m.best_iteration is the round with the lowest validation loss, used by predict() for the OOF slice, appended to iters and printed as fold k: best_iter=…. Log-loss rather than the competition metric is monitored on purpose: the metric depends on a threshold not yet chosen, whereas log-loss selects the round at which probabilities are best calibrated across the range the sweep explores.

After the sweep, the final model is refitted once on every training pair with a fixed int(np.mean(iters) * 1.1) rounds. No held-out data remain, so early stopping is unavailable and the length is transferred from cross-validation: the mean best iteration, scaled by 1.1 because a model fitted on all groups rather than four fifths benefits from slightly more rounds, truncated to an integer. The refit reuses params, so the probability scale on which best_thr and best_ratio were selected is preserved as closely as a refit permits. Test pairs are scored with model.predict(fte[feats]), where fte comes from the same block() and features() path (see Chapter 4).

Risk. The threshold and ratio are selected on the same OOF probabilities that report the validation score, over 31 × 6 = 186 configurations, so the printed OOF macro F0.5 is mildly optimistic; Chapter 10 discusses a nested check. Separately, the refit model has seen no French record and trees cannot extrapolate beyond the training value ranges; the bounded similarities of Chapter 7 limit this exposure, and the per-country match-rate log line for the test split is the only in-pipeline signal for it.

8.6 Reading the gain importances

After the refit, main() computes model.feature_importance("gain"), indexes it by feats, sorts it descending and prints the top 15. Gain is the total reduction of the training objective attributed to splits on a feature, summed over all trees; it has no sign and is not a coefficient. Three readings are useful. High gain for cos_full, n_tset or cos_full_gap1 confirms that name similarity and its context dominate. Gain on the ternary and conflict features (postal_state, house_state, num_conflict) shows the model separating near-duplicates by address evidence, where precision is won. Near-zero gain, for instance on n_acronym or has_alias, means the feature is rare or absorbed by another; it is a removal candidate only once the OOF score is shown not to move. Measured values belong in Table 8.3 (Section 8.8).

9 Decision Layer: From Probabilities to Match Lists

The matcher of Chapter 8 emits one probability per candidate pair; the leaderboard scores one list per Source 1 (S1) entity. This chapter describes the layer between the two: decode_table(), which assigns each Source 2 / Source 3 (S2/S3) record to the S1 entity that scores it highest and records the best probability per (S1, source) group; decide(), which keeps a pair only if it clears an absolute threshold thr and a relative bar ratio · best; the 186-point out-of-fold (OOF) grid that selects both parameters by maximising macro F0.5 including singletons; and to_lists() with the TSV writer. It derives from the metric why a second candidate must be nearly as confident as the first to be worth adding.

9.1 Role of the decision layer

The metric is macro-averaged over S1 entities (see Chapter 2): each contributes one F0.5 computed from its predicted and ground-truth lists, and a singleton, an S1 entity with no true match, contributes 1.0 if and only if its predicted list is empty. The matcher is trained with a pairwise log-loss and knows nothing about lists, singletons or the precision-recall asymmetry; all of that is handled after the model, in decode_table(), decide(), to_lists() and the writer loop of main(). Because the metric logic sits in a small parameterised layer, the expensive stages run once and the operating point is re-selected cheaply from stored OOF probabilities. Figure 9.1 shows the flow.

9.2 decode_table(): assignment and group maxima

The function takes the feature table f and the probability vector prob (OOF probabilities in training, the refitted model's predictions at test time) and returns a reduced table with columns i1, i2, is_s3, p and best:

def decode_table(f, prob):
    d = f[["i1", "i2", "is_s3"]].copy()
    d["p"] = prob
    d = d.sort_values("p", ascending=False).drop_duplicates("i2").reset_index(drop=True)
    d["best"] = d.groupby(["i1", "is_s3"]).p.transform("max")
    return d

9.2.1 One S1 entity per S2/S3 record

Sorting by p descending and calling drop_duplicates("i2") keeps, for every S2/S3 row index i2, only the highest-probability pair. The justification is structural: Source 1 is the de-duplicated reference source, so two S1 entities are two different businesses, and one S2/S3 record can belong to at most one of them. Blocking (see Chapter 6) routinely retrieves the same S2/S3 record for several S1 entities (chain branches, franchises, common names); at most one can be right, every other is a false positive, and on a singleton it costs the full 1.0.

The step is a greedy assignment: when the matcher ranks the correct S1 entity highest, the competing false positives vanish at zero recall cost; when it ranks a wrong entity highest, the true owner loses the record to a false positive that a flat threshold would have produced anyway. The net effect is positive whenever the ranking across S1 entities beats chance, which the cross-record features cos_full_gap2, rank2 and n_cand2 of Chapter 7 support.

9.2.2 The per-(S1, source) maximum

After de-duplication, best is the maximum probability among the surviving pairs of the same S1 entity and source (S2 or S3, read from is_s3); a record claimed by another S1 entity no longer counts towards its former entity's maximum, so the relative rule compares each pair only against competitors that are actually available. Grouping by source rather than by entity alone reflects the ground truth: one business can legitimately appear once in Source 2 and once in Source 3, so a strong S2 candidate must not suppress a moderately confident S3 candidate. Within one source the problem statement allows several records per business; how common that is, reported by profile() as the mean and maximum match count, is what the OOF sweep of Section 9.5 weighs when it sets the strictness of the relative rule.

9.3 decide(): an absolute and a relative bar

def decide(d, thr, ratio=0.0):
    return d[(d.p >= thr) & (d.p >= ratio * d.best)]

A pair survives if its probability is at least thr and at least ratio times the best probability in its (S1, source) group. The best pair of every group satisfies the second condition trivially, so the relative bar only ever removes secondary candidates. ratio = 0 makes it vacuous and reproduces a flat per-pair threshold; ratio = 1.0 keeps at most one pair per (S1, source) group, barring exact ties; the values between interpolate.

A relative rule suits a per-entity metric because the cost of a candidate depends on what the entity already predicts. Take an S1 entity whose best S2 candidate has p = 0.95 and whose second has p = 0.55. A flat threshold of 0.5 keeps both; ratio = 0.7 drops the second, since 0.55 < 0.665. Such a candidate may be a genuine second record or a similarly named different business, and Section 9.4 shows that the metric rewards keeping it only when its probability is well above one half. An entity whose sole candidate has p = 0.55 keeps it under both rules, because there is no stronger competitor to be dominated by. The rule thus prunes weak secondary candidates in crowded groups while sparing lone, moderately confident ones, which one global threshold cannot express.

9.4 Metric arithmetic behind the rule

Let an S1 entity have n > 0 true matches. With P predicted ids of which tp are correct, precision is tp / P, recall is tp / n, and F0.5 = 1.25·P·R / (0.25·P + R), as implemented in f05(). Two consequences shape the decision layer.

9.4.1 Singleton economics

For a singleton the score is binary: 1.0 for an empty prediction, 0.0 for any other, so a false merge on a singleton is the largest single loss available, whereas a missed match on a non-singleton loses only a fraction of its score; the singleton share logged by profile() sets the price of a lenient threshold. A two-outcome model makes this explicit: if an entity's only candidate is true with probability a (in which case the entity has exactly that one match) and, when false, the entity is a singleton with probability b, predicting it has expected score a and predicting nothing has expected score (1 − a)·b. The candidate pays only when a ≥ b / (1 + b): 0.50 when a wrong candidate always means a singleton, 0.33 when it does so half the time. The sweep of Section 9.5 replaces these assumptions with the empirical OOF distribution, but the direction is fixed: more singletons, higher optimal thr.

9.4.2 Break-even for a second candidate

Suppose the entity already predicts one correct candidate and a second with probability q is under consideration. One correct prediction gives P = 1, R = 1/n and F0.5 = 5 / (n + 4). Adding the second gives P = 1, R = 2/n and F0.5 = 10 / (n + 8) if it is true, or P = 1/2, R = 1/n and F0.5 = 5 / (n + 8) if it is false. The expected score with two predictions, 5·(1 + q) / (n + 8), exceeds 5 / (n + 4) if and only if

q ≥ 4 / (n + 4).

9.6 to_lists(), ordering and the writer

def to_lists(d, s1, other, col="i2"):
    out = {e: [] for e in s1.entity_id}
    ids1, ids2 = s1.entity_id.values, other.entity_id.values
    for a, b in zip(d.i1.values, d[col].values):
        out[ids1[a]].append(ids2[b])
    return out

to_lists() converts a table of row indices into a dictionary from S1 entity_id to a list of S2/S3 ids. It is pre-populated with an empty list for every S1 entity, so an entity with no surviving pair is present as a singleton rather than missing, as the one-row-per-entity rule requires. The decoded table is still in descending p order after decide(), so each match list runs from the most to the least confident id. For the candidate file, main() passes the unfiltered fte[["i1", "i2"]], so those lists follow blocking order and matches are a subset of candidates by construction.

The writer in main() iterates over te1.entity_id.values in source-file order and emits a header and one tab-separated line per entity; col is matched_entity_ids for matching_results.tsv and candidate_entity_ids for candidate_pairs.tsv, the column names required by the problem statement:

fh.write(f"source1_entity_id\t{col}\n")
for e in te1.entity_id.values:
    fh.write(f"{e}\t{','.join(dict.fromkeys(lists[e]))}\n")

dict.fromkeys() removes duplicate ids while preserving order, which a set would not. Duplicates cannot in fact arise, since drop_duplicates("i2") leaves each S2/S3 id at most once in the whole matching file and block() de-duplicates (i1, i2) pairs before features are computed; the call guards the rejection rule "no duplicate entity IDs within a single ID list" (see Chapter 2) against upstream changes. An empty list renders as the id, a tab and nothing else, the required singleton format; newline="" keeps line endings at exactly \n. Chapter 11 covers packaging.

Design note. A single global (thr, ratio) is selected on US and Indian OOF data and applied unchanged to France, whose probability distribution the model has never seen. Two extensions follow. Per-source parameters would let S2 and S3 differ in strictness, today reflected only in the is_s3 matcher feature and the per-source grouping of decode_table(): the grid becomes (thrS2, thrS3, ratio) inside the same OOF loop. Per-country parameters would be selected for US and India separately and, for an unseen country, replaced by the more conservative of the two, since a false merge costs more than a missed link. Both add conditions to decide() only; the per-country match rate logged by main() is the check for France (see Chapter 14).

10 Validation Strategy and Tooling

The test set carries no labels, so every number that guides a design decision comes from the training split. This chapter describes the grouped out-of-fold (OOF) protocol inside main() and its diagnostics, the stand-alone scorer utils/score.py, the addition needed to feed it a train-side prediction file, the validator utils/validate_submission.py and every rule it enforces, an error-analysis playbook, and the pre-upload checklist. Throughout, macro F0.5 with all-or-nothing singletons is measured exactly as the organisers compute it, on entities the model has never seen.

10.1 Validation protocol

10.1.1 Grouped out-of-fold predictions

The problem statement asks participants to hold out part of the training data and score it with the F0.5 formula (see Chapter 2). The pipeline uses K-fold cross-validation instead of a single hold-out, so that every training pair is scored by a model that never saw it. main() splits the labelled candidate table ftr with GroupKFold(args.folds), five folds by default, grouped by ftr.i1, the S1 row index. Grouping by S1 entity is essential: the contextual features of Chapter 7 (cos_full_gap1, rank1, n_cand1 and their siblings) and the decision rule of Chapter 9 both act on the whole candidate set of one S1 entity. Spreading that set across folds would overstate what happens on the test set, where every S1 entity is new.

Within each fold, LightGBM trains for at most 2,000 rounds with early stopping after 100 rounds without improvement of the held-out log-loss (see Chapter 8). The held-out predictions at best_iteration fill the vector oof; the final refit uses int(np.mean(iters) * 1.1) rounds, so the OOF run also fixes the capacity of the deployed model.

10.1.2 Scoring the OOF predictions with the official metric

The OOF probabilities are decoded exactly as test probabilities are: decode_table(ftr, oof) assigns each S2/S3 record to its highest-probability S1 and records the per-(S1, source) maximum, and decide() applies the absolute threshold thr and the relative bar ratio · best. For each of the 186 grid points (six ratios in {0.0, 0.6, 0.7, 0.8, 0.9, 1.0}, thirty-one thresholds from 0.20 to 0.95 in steps of 0.025), to_lists() builds per-entity id lists and macro_f05() averages f05() over tr1.entity_id.values. The key set is every training S1 entity, not only those with candidates, so an entity whose true matches were never blocked contributes 0.0 and singletons contribute 1.0 or 0.0: blocking loss and the singleton penalty are inside the estimate. f05() implements the challenge rule literally: empty truth scores 1.0 if and only if the prediction is empty, an empty prediction against non-empty truth scores 0.0, zero true positives score 0.0, otherwise F0.5 = 1.25·P·R / (0.25·P + R). The best grid point is logged as OOF macro F0.5 = … at thr=… ratio=…, the primary estimate of the leaderboard score.

Design note. The OOF number is a tuned score, not an untouched hold-out: (thr, ratio) is chosen by maximising it over 186 points. With only two free parameters selected against the full set of training S1 entities the optimistic bias is expected to be small, but the public leaderboard should be expected to sit slightly lower even for US and India, before any effect of the unseen French records.

Two things lie outside this protocol. The TF-IDF vectorisers and the contextual features are computed on the full training split before folding; they use no labels, and block() refits the vectorisers on test text in the same way, so this mirrors inference rather than leaking. France has no labels, so the only check for the unseen country is the per-country fraction of test S1 entities that received a match, printed as the last line of main() (see Chapter 14).

10.5.1 Difference to the official validator

The official helper, as described in the problem statement, treats a matched id that never appeared as a candidate as a warning; this validator treats it as an error. The pipeline satisfies the subset property by construction, since decide() only selects rows of the blocked candidate table and both files are written from the same fte frame, so a violation can only come from a packaging bug, files from two different runs or a hand edit, which the problem statement itself calls a pipeline bug. Promoting the check to a failure ensures it cannot be scrolled past. When the candidate file is omitted, the validator prints a WARNING rather than a clean pass, because the subset rule is part of what the organisers audit (see Chapter 13).

Risk. A stale or partial copy of the test set under --test-dir makes rule 10 fail for every id the copy lacks or, worse, lets rule 12 pass on an incomplete submission. Table 10.3 therefore requires that the validator and the pipeline read the same dataset/test directory.

10.6 Error-analysis playbook

With train_oof_matching.tsv, train_candidates.tsv, the ground truth and train_source1.tsv in hand, failures are attributed in a fixed order.

  1. By country. Run the scorer with --source1. If the weaker country's blocking recall in the log also trails, the cause lies in normalisation or blocking (the abbreviation tables, the postal regex _postal, the top-k of the address view), not in the model.
  2. By truth size. Run with --by-size. A weak bucket 0 means false merges: raise thr or inspect the features that let a singleton's best candidate pass. A weak bucket 1 with healthy blocking recall means the matcher ranks the true record below the threshold. A weak 3+ bucket implicates the relative rule (p < ratio · best) or the assignment in decode_table().
  3. By source. The scorer has no source flag; restrict both truth and prediction lists to ids beginning with S2- (then S3-) and score each restriction. Read with the blocking recall by source log line, this shows whether S3's field quality (feature is_s3) warrants its own operating point (see Chapter 14).
  4. By failure class. For each entity scoring below 1.0, classify each missing true id as a blocking miss (absent from train_candidates.tsv), a threshold miss (below thr), a ratio suppression (below ratio · best) or an assignment loss (given to another S1 by drop_duplicates("i2")); classify each spurious id as a singleton merge or an over-inclusion. The last two are the classes F0.5 penalises most and are read next to the raw strings to find the noise pattern responsible (see Chapter 3).

Every change to a table, a top-k or a feature is followed by a full rerun of the OOF loop, because the operating point is re-selected on the new probabilities and a gain in one bucket can move thr and cost singletons elsewhere.

11.1.1 The writer code path

Duplicates inside a list are already impossible upstream: block() ends with drop_duplicates() on (i1, i2) and decode_table() keeps each S2/S3 row for one S1 only, so dict.fromkeys() is a guard, not a repair. An empty list joins to the empty string, so a singleton row is the id, a tab and a newline, exactly the third example row of the problem statement.

11.2 candidate_pairs.tsv: the set the model scores

The problem statement defines candidate_pairs.tsv as the exact set of records fed to the matching model for inference, not the output of an early blocking pass that is later filtered. The pipeline meets this definition literally. cte = block(te1, te2) is the only candidate-generation stage; fte = features(cte, te1, te2) starts from cand.copy() and only assigns columns, so it neither adds nor removes rows; pte = model.predict(fte[feats]) scores every row; and cands = to_lists(fte[["i1", "i2"]], te1, te2) converts the same rows to id lists. The organisers' recall-ceiling and reduction-ratio analysis of this file therefore describes precisely what the LightGBM model saw.

The subset property follows from the same flow. decode_table(fte, pte) takes fte[["i1", "i2", "is_s3"]], attaches probabilities and drops rows via drop_duplicates("i2"), but never creates any; decide() is a boolean mask over that table. Every row of matches is thus a row of fte, and the validator's cross-check can fail only when the two files come from different invocations.

Design note. The candidate file is much larger than the match file: each S1 entity carries up to 25 + 25 + 10 + 10 = 70 candidates before the per-view sc > 0.05 cosine cut and the de-duplication of the union (see Chapter 6), against the few that survive decide(). Because F0.5 is precision-weighted and a singleton scores 1.0 only when predicted empty, the gap between the files is the visible record of how much the matcher and decision layer remove.

11.5 Determinism

Most of the pipeline is a pure function of the data and library versions: TfidfVectorizer vocabularies, the sparse products in topk_sparse(), np.argpartition, rapidfuzz scores, GroupKFold (which never shuffles) and the (thr, ratio) grid. The stochastic component is LightGBM. The params dictionary in main() sets feature_fraction=0.8, bagging_fraction=0.8 and bagging_freq=1, so every tree is grown on a random 80 % of rows and columns, but sets no seed. LightGBM then uses its built-in default seeds, which keeps a single-threaded run repeatable, while n_jobs=-1 lets histogram construction be split across threads in an order that varies between machines and builds. The OOF probabilities, the fold best iterations, the refit round count int(np.mean(iters) * 1.1) and a few borderline decisions can therefore differ between environments.

The recommended follow-up is to add seed=42, deterministic=True and force_row_wise=True to params, so that LightGBM neither draws unseeded samples nor picks its histogram strategy by timing; this costs some speed and changes nothing in the OOF sweep or the decision layer. A minor second source is tie-breaking: decode_table() sorts by probability with the default quicksort, which is not stable, so bit-identical probabilities could be ordered differently across NumPy versions; kind="stable" removes this. Documentation_template.md already calls for a seed for bit-exact reproduction.

12 Performance, Complexity and Scalability

This chapter gives the cost model of er_pipeline.py: the asymptotic complexity of every stage, the memory bounds that topk_sparse() and pair_cos() enforce by construction, time and memory estimates for three hypothetical dataset sizes, the knobs that trade recall, precision and run time, how to locate hot spots from the timestamps that log() prints, and the parallelism the code does and does not exploit. The pipeline has not yet been run on the competition data; every number a run would measure is marked as an estimate or left as a placeholder.

12.1 Notation and cost model

|S1| is the number of Source 1 records of a split, |B| = |S2| + |S3| the number of Source 2 and Source 3 records that load_split() concatenates, and |S1c|, |Bc| the per-country blocks that block() forms by grouping on country_n. P is the number of candidate pairs, F = 38 the number of feature columns produced by features() (every column except i1, i2, y), R the number of boosting rounds trained, and nnz the number of non-zeros of a TF-IDF row. Train and test both pass through prep() → block() → features(), so per-split costs are paid twice; cross-validation, refit and the decode grid are paid once.

Two quantities dominate: the dense cell count of retrieval, Σc |S1c| · |Bc| per view, quadratic within a country because topk_sparse() materialises the score matrix with toarray(); and P, which bounds the feature stage, the model and the output, and is at most (kname + kfull + kaddr + kpostal) · |S1| = 70 · |S1| before the union removes duplicates and the cosine floor of 0.05 drops empty overlaps.

12.2 Asymptotic complexity per stage

12.2.1 Normalisation and TF-IDF

prep() applies basic(), expand(), core_name(), name_parts() and the regular expressions _dotted, _punct and _space (inside basic()), _postal, _digits and _ALIAS once per record, O((|S1| + |B|) · L) for average field length L, in pure Python. block() then fits three TfidfVectorizer instances (char_wb, ngram_range=(2, 4), min_df=2) on the concatenated texts of each view and transforms both sides. The analyser is Python code emitting about three n-grams per character, so fitting plus transforming is O(3 · (|S1| + |B|) · L), and each row holds roughly 3L non-zeros at 8 bytes each (float32 value, int32 index); the full view, name_c + " | " + addr_c, has the longest rows.

12.2.2 Top-k retrieval

For every country and fuzzy view, topk_sparse(A[i1], B[i2], k) multiplies a chunk of S1 rows by the transposed block BT, densifies, and runs np.argpartition per row. The sparse product costs Σg dfA(g) · dfB(g) over n-grams g, close to the dense bound because almost any two records share a frequent bigram; toarray() and argpartition are exactly Θ(|S1c| · |Bc|). The stage is O(3 · Σc |S1c| · |Bc| · nnz), and country partitioning is what makes it affordable: two equal countries halve the cell count, while the open-set fallback for an unseen label costs a full |S1unseen| · |B| product (see Chapter 6). The postal view adds Σp |S1p| · |Bp| cells, normally negligible, plus one Python iteration and one B.T.tocsr() per postal code, so its cost is call overhead rather than arithmetic.

12.2.3 Union, pair cosines and features

The chunks are stacked with np.vstack and reduced by drop_duplicates(), O(Praw) with Praw ≤ 70 · |S1|; pair_cos() then computes the three cosines in slices of 200,000 pairs, O(P · nnz). features() is a sequence of list comprehensions: ten rapidfuzz calls per pair (fuzz.ratio, token_sort_ratio, token_set_ratio, partial_ratio, JaroWinkler.similarity, fuzz.ratio on the full name, at least one token_sort_ratio for n_alias_best, three address scorers) plus the Python-level jacc(), initials, acronym and number-set checks. Each scorer is O(|a| · |b|) worst case but runs in C++ on short strings, so the Python-to-C boundary dominates and the stage behaves as O(P) at tens of microseconds per pair. The context features (_gap1, _gap2, rank1, rank2, n_cand1, n_cand2) are vectorised group-by transforms, O(P log P) at most.

12.2.4 Matcher and decode grid

With GroupKFold(args.folds) each fold trains on (1 − 1/folds) · P rows for up to 2,000 rounds with early stopping at patience 100; histogram boosting costs O(rows · F · R) per fit, scaled by feature_fraction=0.8 and bagging_fraction=0.8, and the refit runs 1.1 · mean(best_iteration) rounds on all P rows. Prediction is O(P · R). decode_table() sorts once, O(P log P), and drop_duplicates("i2") leaves |d| ≤ min(P, |B|) rows, which keeps the grid off the P axis. The sweep has 6 ratios × 31 thresholds (np.arange(0.20, 0.96, 0.025)) = 186 points, each a vectorised mask in decide(), a Python loop over kept rows in to_lists() and a loop over all S1 entities in macro_f05(): O(|d| + |S1|) per point at a few microseconds per entity.

12.3 Memory model

The two stages that could allocate proportionally to |S1| · |B| are bounded by construction. In topk_sparse() the chunk is max(16, int(max_cells // n_b)) with max_cells = 2e7, so the dense float32 score block never exceeds about 80 MB (the floor of 16 rows only matters beyond 1.25 million rows in a block), the full-width int64 output of np.argpartition about 160 MB, and the nearly dense sparse product a further 160 MB; the top-k slice is taken with .copy() so the full-width array is released every iteration rather than pinned by a view (Figure 12.2 in 12.6). pair_cos() bounds its transient through slices of 200,000 pairs. Neither bound depends on block size, so an unseen country falling back to all of B costs time, not memory.

What grows is per-pair state. The feature frame holds about 40 columns of 8 bytes, 320 bytes per pair; inside features() the row-aligned copies L and R and the lists of string tuples roughly triple that. During cross-validation ftr.iloc[a][feats] and the validation slice make float64 copies of about 300 bytes per row beside the binned LightGBM Dataset, and ftr is still referenced while fte is built, so both frames are resident at test time. The TF-IDF matrices, about 3.2 KB per record for three views at 400 non-zeros per record, are local to block(). 12.6 Parallelism and optimisation opportunities

Only LightGBM is multi-threaded. The char_wb analyser, the SciPy sparse product, np.argpartition, the rapidfuzz comprehensions, the pandas group-bys and the decode grid run on one core, so on a four-core machine three cores idle for roughly two thirds of the run at the medium size. Three changes, none altering an output value, would recover most of that:

  1. Vectorised string scoring. Recent rapidfuzz releases provide rapidfuzz.process.cpdist(queries, choices, scorer=..., workers=-1), which scores the i-th query against the i-th choice in C++ threads and returns a NumPy array; one call per feature replaces each comprehension in features() and uses every core. process.cdist is the all-pairs variant, appropriate only inside one small block. requirements.txt pins only rapidfuzz>=3.0, and cpdist is absent from the earliest 3.x releases, so the installed version must be checked.
  2. Process pools for retrieval. The per-country, per-view loop in block() is embarrassingly parallel, since each topk_sparse() call touches only its own row slices; a concurrent.futures.ProcessPoolExecutor over (country, view) tasks multiplies throughput by the core count at the price of one bounded transient per worker (Figure 12.2).
  3. Vectorised grid. Replacing to_lists() and macro_f05() by group-by counts of true positives per S1 entity makes each grid point O(|d|) NumPy work, so a finer threshold step becomes free.
Design note. The single-threaded loops are kept because they make the feature definitions readable and auditable for the fair-play review of Chapter 13; the optimisations above preserve every feature value and head the roadmap of Chapter 14.

13.2.2 The rapidfuzz install fallback

The one statement that can reach the network sits in the import block: if importing fuzz and JaroWinkler from rapidfuzz raises ImportError, the script runs os.system(f"{sys.executable} -m pip install -q rapidfuzz") and retries both imports. It is nonetheless the one line a reviewer scanning for network activity will stop at.

Risk. The pip install fallback is unpinned and environment-dependent. Offline, it fails silently inside os.system(), the second import raises ImportError, and the run aborts before reading any data. Online, it may resolve a rapidfuzz release newer than the one behind the submitted outputs, shifting the similarity scores at the last decimal and, through the tuned threshold, a few near-boundary decisions. Neither breaks a rule, but both weaken the "anyone can regenerate both output files" promise. The remedy is to pin rapidfuzz to an exact version in requirements.txt, install it before the run as the README instructs, and delete the except ImportError branch so a missing dependency fails loudly. On Kaggle the package is pre-installed and the branch never executes.

13.3.2 Parameter count

The size bound follows from params and the training loop alone. Each fold trains up to 2,000 rounds with lgb.early_stopping(100), iters collects each fold's best_iteration, and the final refit in main() uses int(np.mean(iters) * 1.1) rounds, so even if every fold ran to the cap the deployed forest holds at most 2,200 trees. With num_leaves=63, a binary tree stores 62 internal nodes (a feature index and a threshold each) and 63 leaf values, about 187 numbers, so the worst case is roughly 2,200 × 187 ≈ 4.1 × 105 numbers, a factor of about 2 × 104 below the 8 × 109 ceiling. The actual tree count is a run-time quantity and is recorded in the placeholder table of Chapter 11 rather than estimated here. The three TF-IDF vocabularies are preprocessing artefacts, not model parameters, bounded by the distinct 2–4-character n-grams with min_df=2 in the provided texts. The 38 input columns of feats (every column of the feature frame except i1, i2 and y) are listed in Chapter 7.

13.4 Output-format constraints by construction

Constraints 1 to 4 concern the two TSV files, and each is satisfied by a specific construct. to_lists() starts from {e: [] for e in s1.entity_id}, so every test S1 entity owns a row before any pair is appended, and the writer iterates te1.entity_id.values once; missing and duplicate rows are both impossible. Self-matches are excluded because load_split() returns pd.concat([s2, s3]) as the only "other" frame, block() draws i2 from it alone, and to_lists() maps i2 through other.entity_id.values. Unknown ids are excluded because every emitted id string was loaded by read_tsv() from the test S2/S3 files with dtype=str and quoting=3. Duplicates within a list are removed at up to three points: drop_duplicates() on the (i1, i2) table in block(), which already makes candidate_pairs.tsv duplicate-free; drop_duplicates("i2") in decode_table(), which additionally assigns each S2/S3 record to a single S1 entity in matching_results.tsv; and dict.fromkeys() in the writer, an order-preserving safety net for both files. Matches are a subset of candidates, and candidate_pairs.tsv is the exact inference set, because decide(), cands and model.predict(fte[feats]) all operate on the same fte frame. The stdlib validator of Chapter 10 re-checks all of this from the files alone.

13.5 Country as an open set

The problem statement forbids hard-coding, filtering or one-hot encoding the pipeline to {US, India}. The country label enters the code at two points: prep() normalises it through basic() into country_n, a free string, and block() partitions the S1 frame by groupby("country_n"), whatever values occur, comparing a group whose label has no S2/S3 counterpart (or a blank label) against every S2/S3 record instead of an empty block; the continue that guards this loop fires only when the whole S2/S3 frame is empty. Country is not a model feature: features() emits no country column and no column derived from one, so the booster cannot learn a US- or India-specific branch; the only source indicator is is_s3, taken from the entity-id prefix. French legal forms and address idioms sit in NAME_ABBR (cie, ste), LEGAL (sarl, sas, eurl, …), ADDR_ABBR (fbg, chem, imp) and ADDR_STOP (de, la, des, …) as generic normalisation entries applied to every record, not as a country branch, so a French test entity takes the same path as a US one and is written to both files.

Design note. best_thr and best_ratio are tuned on US and Indian out-of-fold predictions, the only labelled entities. Under a precision-weighted F0.5 with all-or-nothing singleton credit, an operating point too permissive for France costs more than one too strict; the per-country match-rate line logged at the end of main() checks that France is neither starved nor over-matched (see Chapter 14).

13.6 Auditability of blocking

The organisers use candidate_pairs.tsv to measure the recall ceiling and reduction ratio of blocking and to verify the pipeline. The file supports that audit directly: it is the full fte[["i1", "i2"]] table converted to id lists, with no filtering between it and model.predict(), so the reduction ratio 1 − |pairs| / (|S1| · |S2 + S3|) can be computed from the file and the test sources alone. On the training split the same block() call is scored against the labels and logged: the pair-level recall ceiling, the count of S1 entities with at least one true match blocked (the quantity the macro metric actually depends on), recall by country and by source, the all-candidates floor and the blocking-oracle ceiling. A reviewer can therefore confirm that the submitted candidate set came from a stage whose behaviour was measured on labelled data, not tuned on hidden information; the values themselves are to be filled from the run log (Chapter 11). The remaining sources of run-to-run variation, unseeded bagging and dependency drift, are catalogued in Chapter 11 and carried into the risk register of Chapter 14.

The pipeline of Chapters 4 to 11 is a complete baseline, but it has not yet been executed on the real data, and several design choices are deliberate simplifications. 14.2.1 The blocking ceiling

The matcher only sees pairs that block() produces, and the union of four views (core name k=25, name-plus-address k=25, address k=10, same-postal name k=10, each cut at cosine 0.05) is a finite budget. A true match outside all four lists is unrecoverable, and because the metric is macro-averaged per Source-1 entity the loss is concentrated: an entity whose single true match is missed scores exactly 0. For an entity with m true matches of which the blocker retrieves m−1 and the matcher accepts exactly those, precision is 1 and recall is (m−1)/m, so F0.5 = 1.25·R/(0.25+R) gives 0.833 for m=2 and 0.909 for m=3. Records whose name and address are both heavily rewritten, or whose name is in a non-Latin script, are the most likely to fall outside every view; the log line "S1 entities with >=1 true match blocked" measures this on the training split.

14.2.2 Coverage of the normalisation tables

NAME_ABBR holds 18 entries and ADDR_ABBR 41, written from the problem statement's noise list, not learned from the data. Any abbreviation absent from the tables is left to the fuzzy features, which penalise mfrs against manufacturers as heavily as a typo. Several expansions are ambiguous and applied unconditionally: st becomes street even in st louis, ste is suite in addresses but societe in names, and in addresses the single letters n, s, e, w become compass points even when they are initials of a landmark or a person. Hindi-transliteration coverage is limited to marg, salai, ngr, clny, sec, chowk and mg; alternations such as sri/shri are handled only implicitly by n-gram overlap, and the French list covers legal forms and four street types. Because basic() encodes to ASCII with errors="ignore", a string written entirely in Devanagari collapses to the empty string, its TF-IDF row in the name view is all zeros, and the record can be blocked only through the address view or the address half of the name-plus-address view; the same-postal view ranks by name cosine and therefore never returns it either.

14.2.3 The unseen country and feature drift

No French pair contributes to the LightGBM training set or to the (thr, ratio) sweep, so behaviour on France is an extrapolation. The design mitigates this (Chapters 5 to 7): normalisation is language-agnostic, the vectorisers are refitted on the test corpus inside block(), and the context features (cos_full_gap1, rank1, n_cand1 and their i2 counterparts) are relative rather than absolute. Those context features are also the second concern: computed by groupby over the candidate table, their distribution depends on how many candidates each record collects, hence on block size, view overlap and country. If French blocks differ in size from US and Indian ones, n_cand1 and the gap features shift and tree splits may be systematically off. The only test-time signal is the per-country match rate that main() logs: a French rate far from the seen countries' is a warning, not a diagnosis.

14.2.4 Decision-layer simplifications

The decision rule (Chapter 9) is where precision is bought, and it is deliberately simple. One thr and one ratio serve all countries and both sources; if the OOF-optimal threshold for India differs from the US one, the global value under-matches one and over-matches the other, and France inherits a compromise it was never measured on. Second, decode_table() assigns each S2/S3 record to at most one S1, and decide() compares each pair with the best of its (i1, is_s3) group, but the S2 and S3 matches accepted for the same S1 are never compared with each other. An S1 entity may accept an S2 record at one address and an S3 record at another; whichever is wrong is a false positive. On a two-match entity that accepts one correct and one wrong record, P = R = 0.5 and the score falls from 1.0 to 0.5; on a one-match entity that accepts its true record plus a wrong one, P = 0.5, R = 1 and the score is 0.556.

14.2.5 Throughput

features() evaluates about twenty rapidfuzz and Python-level expressions per pair inside list comprehensions, and the sweep calls to_lists() and macro_f05(), both Python loops, 6 × 31 = 186 times. Chapter 12 estimates the rapidfuzz loop as the third-largest block of wall-clock after retrieval and cross-validation, and the grid as minor; none of these has been timed on the real data. The effect on the score is indirect: the candidate budget k is chosen with this cost in mind, so a faster feature stage permits a larger k and a higher recall ceiling at the same wall-clock.

14.4 Roadmap

The roadmap has three horizons ordered by effort and by confidence that the change improves macro F0.5. Every item has one acceptance rule: it is merged only if the OOF macro F0.5 from the GroupKFold loop in main() does not fall, and preferred if the blocking recall ceiling rises. Figure 14.1 shows the sequencing; the horizons are cumulative.

14.4.1 Horizon 1: quick wins

These changes touch a few lines each and carry no licence or resource risk.

  • Per-country and per-source (thr, ratio). The sweep in main() is repeated with macro_f05() restricted to one country's S1 entities. France, having no labels, receives the higher of the two thresholds, because a false positive on a singleton costs 1.0 whereas a missed match costs a fraction.
  • Seed fixing. Adding seed, bagging_seed and feature_fraction_seed to params makes the fold models and the refit deterministic, so the reproducibility claim of Chapter 11 becomes exact.
  • Vectorised string features. Replacing the list comprehensions in features() with rapidfuzz.process.cdist on aligned arrays removes the per-pair Python overhead; the freed budget goes to a larger k_addr or k_postal, the two views with the smallest k (10 each).
  • Phonetic keys. A fifth blocking key from a phonetic encoding of core-name tokens (Double Metaphone or an in-repo consonant-skeleton code, no external data) groups vishwakarma with bishwakarma and sri with shri; it joins the union in block() like the same-postal view.
  • Address-component parsing. A regex split of addr_n into house number, street, locality, city and postal code enables component-wise features, notably a street-name ratio not diluted by landmarks such as near sbi atm.

14.4.2 Horizon 2: learned components

Horizon 2 replaces the two hand-built parts that limit generalisation, the abbreviation tables and the n-gram representation, with learned models, subject to the licence and size rules of Chapter 13.

Pairwise cross-encoder re-ranker. A cross-encoder takes the concatenation name_n | addr_n [SEP] name_n | addr_n of a pair and outputs one match probability, attending across both records, which suits abbreviation, transliteration and word-order noise. It is trained on the OOF-hard pairs (those with oof probability in an illustrative band of roughly 0.2 to 0.8, to be set from the run) plus all positives, so it learns the cases the feature model cannot separate. Its output becomes one more LightGBM feature or, more conservatively, a second-stage re-ranker applied only to pairs within a margin of thr, leaving confident decisions and singletons untouched. 14.4.3 Horizon 3: research directions

  • Graph and transitive decoding. Score S2–S3 pairs with the same feature set, build the graph of accepted and candidate edges, and decode per connected component so that an S1 entity's accepted S2 and S3 records are consistent with each other. This removes the contradiction of Section 14.2.4; the solver rejects, never adds, when evidence conflicts, so the step stays precision-first.
  • Active learning on uncertain pairs. Pairs with OOF probability near thr carry the most information; reweighting them, or training the re-ranker on them first, spends capacity where the F0.5 decision is made.
  • Country-adaptive normalisation. Learn abbreviation expansions from the training pairs by aligning tokens between matched names and addresses, and apply per-country tables in norm_name() and norm_addr(); a new country is covered by unsupervised alignment among its own candidate pairs.
Design note. The order of the horizons follows the metric. Horizon 1 raises precision where it is cheapest (per-country thresholds, a singleton-safe France margin) and recall where it is safest (a larger candidate budget behind an unchanged matcher). Horizon 2 attacks residual errors no string feature can express. Horizon 3 changes the decision structure itself, the step with the highest potential and the highest risk of new false positives, so it comes last.

Open-set labelA categorical field whose test values may not appear in training (country: France). The pipeline never enumerates countries; unseen S1 labels fall back to all S2/S3 records.
NFKD foldingUnicode compatibility decomposition followed by dropping non-ASCII code points; turns Société into Societe. First step of basic().
Legal suffixA corporate-form token (Ltd, LLC, SARL) carrying no identity information; stripped by core_name() using the LEGAL set.
Core namename_c: the normalised name with legal suffixes removed; the primary text for blocking and name features.
DBA / alias marker"Doing business as" and equivalents (t/a, a.k.a., formerly) separating a legal name from a trade name inside one field; split by _ALIAS in name_parts().
ZIP, PIN, code postalUS 5-digit (+4) postal code, Indian 6-digit Postal Index Number, French 5-digit postal code; all captured by _postal.
House numberThe leading digit run of the normalised address (house); compared as a ternary state.
TF-IDFTerm frequency × inverse document frequency weighting of a text vector; here over character n-grams with sublinear_tf (1 + log tf) and min_df=2.
char_wbscikit-learn analyser producing character n-grams only inside word boundaries (words padded with spaces), so n-grams never span two tokens.
n-gramA contiguous sequence of n characters; the vectorisers use n = 2, 3, 4.
Cosine similarityDot product of two L2-normalised vectors; equals the sparse matrix product in topk_sparse() and the row-wise product in pair_cos().
L2 normalisationScaling a vector to unit Euclidean length; TfidfVectorizer does this by default.
Top-k / argpartitionSelecting the k largest scores per row without a full sort; np.argpartition is O(n) per row and returns the k best indices unordered.
Mutual nearest neighbourA pair that is the best candidate for both its S1 entity and its S2/S3 record on cos_full (cos_full_gap1 = cos_full_gap2 = 0, rank1 = rank2 = 1).
Gap featureA pair's feature value minus the maximum over its competitors on one side (*_gap1, *_gap2); zero for the best candidate.
Indel ratio (fuzz.ratio)Normalised similarity based on insertions and deletions, 0 to 100.
token_sort_ratiofuzz.ratio after sorting the tokens of both strings; order-insensitive.
token_set_ratioRatio over the intersection and differences of the token sets; tolerant of extra tokens on one side.
partial_ratioBest fuzz.ratio of the shorter string against any equal-length window of the longer one; substring matching.
Jaro-WinklerCharacter-transposition similarity with a bonus for a common prefix; n_jw.
Jaccard|A ∩ B| / |A ∪ B| over token sets (jacc()) or digit-run sets (num_overlap).
Gradient boosting / LightGBMAn ensemble of decision trees fitted sequentially to the gradient of the loss; LightGBM is the MIT-licensed implementation used by lgb.train().
GroupKFoldCross-validation that keeps all rows sharing a group key (i1) in one fold, so an S1 entity's candidates are never split between training and validation.
OOF (out-of-fold)Predictions for each row made by the fold model that did not train on it; the basis of the (thr, ratio) sweep.
Early stoppingHalting boosting when the validation loss has not improved for 100 rounds; the mean of the folds' best rounds, scaled by 1.1, sets the refit round count.
Threshold (thr) / relative ratio (ratio)The two decision parameters of decide(): absolute probability floor and minimum fraction of the best probability within the (S1, source) group.
Transitive closurePropagating matches along chains (if A~B and B~C then A~C); not applied here because the task is bipartite S1-to-S2/S3, but relevant to the roadmap (see Chapter 14).
Cross-encoderA transformer that reads both records jointly and outputs a match score; a roadmap option constrained to MIT/Apache-2.0 models of at most 8B parameters.
Feature importance (gain)Total loss reduction attributed to splits on a feature across all trees; printed for the top 15.
